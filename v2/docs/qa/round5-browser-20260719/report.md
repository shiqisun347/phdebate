## 问题

### ISSUE-001：同一席位可被两个独立设备同时控制

- 严重度：High
- 分类：权限 / 状态一致性 / 多设备接管
- 房间：`544636`
- 账号：`qa_r5_b_0719`
- 预期：第二设备取得席位控制后，旧设备自动降级为只读观战；同一席位任一时刻只有一个设备能执行准备、取消准备或释放席位。
- 实际：两个独立 Chrome 会话同时显示“取消准备”和“释放当前席位”。第二设备取消准备后，旧设备实时收到状态更新，但仍保留操作权；旧设备随后又能成功确认准备。

复现步骤：

1. 设备 A 的 Round5乙已认领反方一辩并确认准备。[旧设备控制截图](screenshots/issue-001-step-1-old-device-controls.png)
2. 使用同一账号在独立浏览器设备 B 登录并进入房间；设备 B 同样获得取消准备和释放席位控制。[第二设备截图](screenshots/1v1-b-second-device.png)
3. 设备 B 点击取消准备；设备 A 收到“未准备”状态，但仍显示“确认准备 / 释放当前席位”。[旧设备仍可控制](screenshots/issue-001-step-2-old-device-still-controls.png)
4. 设备 A 点击确认准备并成功再次改变房间状态。[结果截图](screenshots/issue-001-result-old-device-mutates.png)

- Repro Video：[issue-001-multi-device-control.webm](videos/issue-001-multi-device-control.webm)
- 建议：房间席位记录权威 `controller_device_id` 和递增 lease；新设备显式接管后发布 `control_revoked`，旧页面立即进入只读，所有写接口同时校验 device lease，而不仅校验 user/seat。

### ISSUE-002：网络中断时直接显示英文底层错误 “Failed to fetch”

- 严重度：Medium
- 分类：错误反馈 / 本地化 / 弱网恢复
- 房间：`855550`
- 视口：390×844 与 1440×900 均可复现
- 预期：准备操作请求断网时显示“网络连接失败，准备状态未改变，请检查网络后重试”，并提供明确重试方向。
- 实际：页面直接显示浏览器底层英文 `Failed to fetch`。准备状态确实保持不变，但普通学生无法判断操作是否生效、是否需要刷新或重试。

复现步骤：

1. 真人席位处于“已准备”，页面提供“取消准备”。[操作前](screenshots/issue-002-step-1-ready-before-offline.png)
2. 中断 `/api/rooms/855550/ready` 请求后点击“取消准备”。
3. 页面保留已准备状态，但错误区域显示 `Failed to fetch`。[错误结果](screenshots/issue-002-result-raw-failed-to-fetch.png)

- Repro Video：[issue-002-network-error-copy.webm](videos/issue-002-network-error-copy.webm)
- 建议：在统一 API 错误映射层将网络异常、超时、离线分别转换为中文可操作文案；写操作失败必须明确“状态未改变”。
