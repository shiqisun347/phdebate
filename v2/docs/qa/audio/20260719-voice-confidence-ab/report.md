# 辩手语音自信感与连续性修复记录

日期：2026-07-19

## 本次上线调整

- MOSS 每轮由服务端注入统一风格指令：自信、坚定、有说服力，重音清晰，短停顿，句尾有力，语速约快 10%，同时禁止喊叫和夸张表演。
- WebSocket 与 HTTP 回退 TTS 路径使用同一指令，浏览器和比赛请求不能覆盖。
- LiveKit mono Opus 目标码率由 48 kbps 提升至 64 kbps。
- 关闭 Opus DTX，避免 TTS 的短停顿反复启停编码器产生细小点击声。
- 服务端 AudioSource 队列由 100 ms 增至 180 ms；浏览器 playout delay 使用 120 ms。

## 生产浏览器门禁

- 专用 1v1 房间完成真实 Agent → MOSS → LiveKit → Chromium AudioWorklet 链路。
- Agent 首个可读字符到浏览器非静音样本：`2710.1 ms`，满足 `< 3000 ms`。
- 稳态 Opus：约 `58–67 kbps`；浏览器报告 `audio/opus`。
- RTP 丢包：`0`。
- 浏览器启动过渡累计 concealed samples：`4039`，约 `84 ms`；随后超过一分钟不再增长。
- 92 秒归档 WAV：无削波、无大于 0.35 的相邻样本跳变，最长内部低能量段 270 ms。
- 专用验收房已终止，没有遗留活动 TTS 任务。

## 结论与边界

技术门禁通过，连续播放和传输质量较上一版稳定。声音是否达到学生辩论场景的主观“自信、自然、不端着”仍需人工试听；若仍显中性，下一步应更换为真实辩论式参考录音，而不是继续提高播放速度或后处理增益。

## 第二轮：发布时钟撕裂修复

提高浏览器缓冲后，一场真实长发言仍在无 RTP 丢包时累计约 0.5 秒
`concealedSamples`。服务端同时持续出现 40–137 ms 的 publisher clock late，最终定位为：

- LiveKit `AudioSource.capture_frame` 已使用原生有界队列进行背压节流；
- 应用发布循环又额外执行一次 20 ms 手工时钟节流；
- 新 generation 清空原生队列后，真实 PCM 无法快速重新填满队列，Python 调度抖动直接变成浏览器解码补偿；
- lobby、paused 和 judging 房间仍维持无意义的静音发布时钟，增加事件循环负担。

修复内容：

- 移除活动 PCM 的第二套手工时钟，以 LiveKit 原生队列作为唯一播放节拍；
- 新发言达到 1200 ms 应用预缓冲前不再向已清空的原生队列重新填入静音；
- 发布器启动静音预填充在 `start()` 返回前完成，消除启动竞态；
- 只为 `preparing` 和 `running` 房间保持发布器，暂停、大厅和裁判阶段释放发布器；
- 服务端原生队列设为 200 ms，浏览器 playout delay 设为 180 ms。

最终生产验收：

- Agent 首字符到浏览器非静音：`2455.3 ms`；
- 浏览器稳定阶段 Opus：约 `59–65 kbps`；
- RTP 丢包：`0`；
- 启动后 concealment 增量：`1671 samples`，约 `34.8 ms`；
- 随后超过 60 秒保持 `3951 samples` 不再增长；
- 新验收房没有新增 `publisher clock late` 日志；
- 验收房已终止，MOSS 无 pending/orphan 会话。

最终结构化证据：

- [首声门禁](./browser-native-queue-final.json)
- [超过 60 秒的稳定播放快照](./browser-native-queue-steady.json)

继续压低剩余约 35 ms 的启动补偿，可能需要更大的播放延迟、替换 LiveKit/浏览器
抖动缓冲策略或更换 TTS 模型，收益已经明显低于成本，本轮不继续增加复杂度。

## 第三轮：残余杂音与撕裂音复核

用户主观试听仍能偶尔听到轻微杂音或撕裂感。为避免破坏已经通过连续性门禁的链路，
本轮只做离线诊断，没有修改 MOSS、LiveKit、Opus 或浏览器播放器。

复核结果：

- 92 秒生产归档音频峰值为 `-0.77 dBFS`，没有削波；最大相邻采样跳变约
  `0.261`，没有发现孤立的硬点击候选。
- 浏览器稳定阶段仍为零 RTP 丢包，`concealedSamples` 在启动后不再增长；现有证据
  不支持持续网络欠载或播放器反复断流。
- 将同一 92 秒源 WAV 离线编码/解码为当前约 64 kbps Opus 后，最大相邻采样跳变
  从 `0.261` 降至 `0.233`，大于 `0.2` 的跳变从 75 次降至 34 次；Opus 没有制造
  新的硬点击。继续提高到约 85–101 kbps 未改善该指标，因此不增加生产带宽。
- 8 个固定音色的参考录音质量不完全一致。第 5 个参考录音的高频能量和相邻采样
  跳变明显偏高，第 6、7 个也比第 1、3、4 个更粗糙。这些参考录音缺陷可能被
  音色克隆带入输出。
- 对参考录音使用常规 `adeclick` 几乎没有改善。8 kHz 低通能降低统计上的高频跳变，
  但会改变音色参考，且必须重启模型并重新完成 8 音色主观 A/B、首声、长发言和
  并发门禁，不能作为无风险热修复。

处置决定：暂不修改生产音频链路。现阶段直接加入实时去点击、低通或提高缓冲的收益
不确定，反而可能使声音发闷、首声变慢或重新引入卡顿。后续若要继续优化，应先换用
干净、无混响、无降噪伪影的同说话人参考录音，在隔离环境完成同文本 A/B 后再替换
固定音色；不要在当前可靠版本上叠加实时后处理。

## 第四轮：问题音色临时隔离

后续生产 1v1 复核再次生成一段 32.72 秒的 `debate_voice_5` 语音，其中大于 0.2 的
相邻采样跳变达到每秒 44.19 次；结合该音色 12 个既有真实样本的统计，已经可以确认
问题并非单次网络抖动。为避免引入高成本实时后处理，反方一辩暂时改用已验证的
`debate_voice_8`。MOSS、LiveKit、Opus 与浏览器播放实现保持不变。详细证据见
[`../20260719-residual-artifact-audit/report.md`](../20260719-residual-artifact-audit/report.md)。

上线后的真实房间门禁为 `2797.9 ms` 首声、零 RTP 丢包；73.20 秒完整归档的大幅
相邻采样跳变由问题样本的每秒 `44.19` 次降至 `0.72` 次。该最小隔离方案通过，未
引入额外实时滤波或播放延迟。
