## 结论摘要

这次测试实际完成了“注册 → 登录 → 查看赛事 → 创建房间 → 输入房间号加入 → 认领席位 → 双方准备 → 房主确认开始 → 正反立论 → 自由辩论举手/换方 → 双方总结 → AI 裁判 → 结果页”的完整链路。房间 `#264011` 最终完成并进入结果页，反方得分 82，正方 0。

但当前版本仍不能作为稳定的学生比赛产品上线。最严重的问题是席位设备控制权：辩手从比赛页进入控制台、刷新、麦克风失败重连或重新打开比赛页后，服务端会返回 `409 POST /api/rooms/264011/control-lease`（`{"force":false}`），前端显示“其他设备已接管”，却没有可点击的接管入口。结果是当前人类辩手无法发言，发言被超时跳过，结果页记录为“正方未在记录中提供任何发言”。这直接造成比赛数据丢失，应列为 P0。

另一个高优先级问题是房主在控制台和观战页之间没有明确的“返回辩手比赛页”路径：大厅公开比赛卡片只进入 `/watch`，观战页提示“请进入比赛控制页”却没有控制台链接，控制台只有“打开观战”，没有返回 `/debate` 的入口。普通学生无法凭页面操作恢复比赛或继续发言，只能猜 URL。

## 已验证正常的流程

- 注册不要求邮箱或手机号，真实姓名出现在房间席位、排行榜和结果页。
- 赛事详情包含介绍、排行榜、观战列表、规则说明和题目列表；创建/搜索房间选择清晰。
- 两个独立账号可以同时在线，第二个账号可用六位房间号进入并认领空席；双方准备状态实时同步。
- 房主在所有真人准备后看到“锁定席位并开始”，点击后有二次确认；开始后席位锁定。
- 房主控制台的“暂停比赛/继续比赛”可以保存并恢复阶段剩余时间；“重置当前发言”可以从保存上下文重新执行。
- 自由辩论的“当前可发言阵营”“本轮剩余”“举手申请下一轮”状态会随双方发言同步变化；观众只能查看举手队列。
- 麦克风被浏览器拒绝时，页面明确提示允许麦克风，并提供“改用文字发言”路径；文本提交可以推动阶段继续。
- 公开观战页和匿名结果页没有显示赛中字幕或赛后发言文字，结果页明确提示“为保护参赛者数据，观众不能查看赛中字幕和赛后发言文字”。
- 1920×1080 页面整体留白、浅色背景、左右队伍卡片和底部固定控制区清晰；390×844 页面保持上方舞台、下方固定主按钮，主按钮没有被底部面板遮挡。

## 问题清单

### ISSUE-001：设备控制权失效后没有可操作的“接管”入口（P0）

| 字段 | 内容 |
|---|---|
| 严重度 | Critical / P0 |
| 分类 | 功能、数据完整性、实时连接 |
| 页面 | `/rooms/264011/debate`、`/rooms/264011/control` |
| 复现视频 | [issue-001-control-lease-repro.webm](browser-room-control-dogfood-20260722/videos/issue-001-control-lease-repro.webm)、[issue-001-control-lease-repro-2.webm](browser-room-control-dogfood-20260722/videos/issue-001-control-lease-repro-2.webm) |
| 网络证据 | [control-flow.har](browser-room-control-dogfood-20260722/control-flow.har)，包含 `409 POST /api/rooms/264011/control-lease` |

**复现步骤**

1. 以房主账号创建房间并开始比赛，进入正方一辩轮次。见 [start-flow-step-5-four-seconds.png](browser-room-control-dogfood-20260722/screenshots/start-flow-step-5-four-seconds.png)。
2. 从比赛页打开控制台，或因麦克风权限失败触发一次实时连接重建，再重新打开 `/rooms/264011/debate`。
3. 在当前席位轮到发言时观察主按钮：页面显示“其他设备已接管”，按钮 disabled；用户没有“接管当前设备”按钮。见 [free-debate-host-turn.png](browser-room-control-dogfood-20260722/screenshots/free-debate-host-turn.png)。
4. 点击“麦克风不可用？改用文字发言”，文本框也显示“该席位已由另一设备控制”；“重试进入文字发言”仍不能获得控制权。见 [control-lease-text-retry.png](browser-room-control-dogfood-20260722/screenshots/control-lease-text-retry.png)。
5. 同一房间的另一位辩手在其轮次也出现相同状态，说明不是单一浏览器会话的偶发显示问题。

**实际结果**

- 浏览器控制台记录 `409 POST /api/rooms/264011/control-lease`，请求体为 `{"force":false}`。
- 前端文字写成“如需切换请确认接管”，但页面没有可点击的确认接管入口。
- 当前人类不能提交语音或文字，阶段超时后继续推进。
- 结果页最终显示“正方未在记录中提供任何发言”，正方评分为空，比赛数据发生实际丢失。见 [result-page-full.png](browser-room-control-dogfood-20260722/screenshots/result-page-full.png)。

**期望结果**

在同一账号的新设备/新页面打开时，页面应给出明显的“接管席位”二次确认；确认后旧连接只读，新连接立即获得控制权。若无法接管，必须暂停本轮并显示可执行的恢复方案，不能静默等待超时。

**建议**

- 将 409 状态专门映射为 `control_conflict`，前端显示“当前席位在另一页面控制”。
- 增加 enabled 的“接管当前席位”按钮，调用 `force=true`，二次确认后使旧连接失效。
- 控制台、文字 fallback、语音页面共用同一个席位接管组件。
- 在服务端将离开/页面隐藏/RTC 断线的控制权释放和新连接接管做成幂等操作，并记录新旧 device_id。
- 接管失败时冻结当前计时，不要因设备锁冲突消耗人类发言时间。

### ISSUE-002：房主无法从控制台/观战页回到辩手比赛页（P1）

| 字段 | 内容 |
|---|---|
| 严重度 | High / P1 |
| 分类 | 导航、房主控制、用户体验 |
| 页面 | `/rooms/264011/watch`、`/rooms/264011/control` |
| 证据 | [control-page-host-authenticated.png](browser-room-control-dogfood-20260722/screenshots/control-page-host-authenticated.png)、[control-page-paused.png](browser-room-control-dogfood-20260722/screenshots/control-page-paused.png) |

**复现步骤**

1. 房主从比赛页进入控制台。
2. 控制台只有“打开观战”，点击后进入 `/watch`。
3. 公开比赛卡片和个人中心中的进行中房间也都链接到 `/watch`。
4. `/watch` 文案写“需要操作时请进入比赛控制页”，但没有“进入控制台”链接；控制台又没有“返回辩手页”链接。

**实际结果**

学生无法从页面可见入口回到 `/debate` 继续发言；只能手工修改地址栏或依赖浏览器后退。对于暂停比赛，页面告诉用户“等待房主处理”，但没有告诉房主如何继续当前席位。

**建议**

在房间内提供统一导航：`辩手比赛页`、`控制台`、`观战`。房主在控制台同时看到“返回比赛页（保留控制权）”；观战页对房主显示“进入控制台”；暂停通知中直接给出“打开控制台并继续/重试”按钮。

### ISSUE-003：正常双人比赛在首轮结束后出现“连续 3 次异常”安全暂停（P1，需继续定位）

| 字段 | 内容 |
|---|---|
| 严重度 | High / P1 |
| 分类 | 比赛流程、可靠性 |
| 页面 | `/rooms/264011/control` |
| 证据 | [control-page-paused.png](browser-room-control-dogfood-20260722/screenshots/control-page-paused.png) |

**观察过程**

在双方都已准备、开始后，正方首轮因设备控制冲突无法提交；阶段结束后系统进入反方立论，控制台出现事件 `#35 状态机异常暂停：连续 3 次异常，已隔离本房间`，页面显示“服务异常暂停”。通过“重置当前发言”后可继续，说明恢复路径有效，但首轮异常被包装成服务异常，房主无法判断是席位控制、语音服务还是状态机问题。

该问题在本次真实流程中出现一次，重置后未再次出现；需要在修复 ISSUE-001 后用干净设备再跑两次确认是否独立存在。

**建议**

安全暂停必须展示可读的根因类别（席位控制冲突、语音权限、Agent、TTS、状态机），并提供针对性动作；不要把人类设备锁冲突显示为泛化的“服务异常”。

### ISSUE-004：阶段切换时“等待下一位”“当前发言人”和计时口径不一致（P2）

| 字段 | 内容 |
|---|---|
| 严重度 | Medium / P2 |
| 分类 | UX、信息架构 |
| 证据 | [start-flow-step-5-four-seconds.png](browser-room-control-dogfood-20260722/screenshots/start-flow-step-5-four-seconds.png)、[free-debate-after-transition.png](browser-room-control-dogfood-20260722/screenshots/free-debate-after-transition.png) |

**实际表现**

- 页面顶部显示当前阶段和当前席位，但中央副标题写“等待下一位辩手”。
- 正方立论从开场提示的约 5–7 秒倒计时切换到完整阶段计时；自由辩论同样先显示短倒计时，再显示总计时和本轮计时。
- 普通学生容易误以为比赛卡住，或者不知道自己现在是“准备”“可开始发言”还是“等待系统播报”。

**建议**

将状态拆成明确的三段：`系统播报中`、`轮到你，可开始发言`、`对方发言中`。倒计时文案使用“开场提示剩余 00:05”“本轮发言剩余 00:15”“阶段总计时 03:43”，不要复用“本环节剩余”造成口径混淆。

### ISSUE-005：控制台的运行状态对纯人类比赛不准确，异常信息难以行动（P2）

| 字段 | 内容 |
|---|---|
| 严重度 | Medium / P2 |
| 分类 | UX、内容 |
| 证据 | [control-after-reset.png](browser-room-control-dogfood-20260722/screenshots/control-after-reset.png) |

**实际表现**

- 1v1 双人房间仍显示“AI 辩手：由系统按阶段自动调用”，容易让用户以为 AI 会替换人类。
- “实时字幕与语音：发言时按需连接”没有显示当前连接/队列/失败原因。
- 事件列表向用户暴露大量低层事件（多次上线/离线、阶段状态更新、自由辩论状态更新），但没有摘要和当前可执行动作。

**建议**

按房间模式展示准确状态：`纯人类席位`、`AI 空席补位`。将事件流分为“对用户的比赛时间线”和“管理员诊断日志”；普通房主只看到当前故障、影响范围、下一步按钮。

### ISSUE-006：页面导航和恢复会反复建立 LiveKit 连接并产生多个设备身份（P2）

| 字段 | 内容 |
|---|---|
| 严重度 | Medium / P2 |
| 分类 | 性能、实时音频、连接管理 |
| 证据 | `control-flow.har`；控制台多次出现 `connecting → connected`，同一账号生成多个 `device:` ID |

**实际表现**

同一场测试中，进入比赛、打开控制台、回到比赛页、打开文字 fallback、重置步骤和重新打开页面都会重新请求 `/api/rooms/264011/rtc-token`，并在 LiveKit 日志中出现多个不同的 `device:` 身份。页面还记录了浏览器自动播放被策略拦截的 `NotAllowedError: play() failed because the user didn't interact with the document first`。

这会放大 ISSUE-001 的控制权冲突，也增加语音断开、重复订阅和音频启动延迟风险。

**建议**

进入房间后复用同一个 RTC 会话和 device_id；控制台不应抢占辩手会话；确需重新连接时先正常释放旧控制权。音频解锁应在房间大厅由用户主动点击一次，并在页面上持续显示“声音已解锁/点击开启声音”。

### ISSUE-007：文字 fallback 进入即占用本轮，缺少“开始编辑”与“确认接管”两步（P2）

| 字段 | 内容 |
|---|---|
| 严重度 | Medium / P2 |
| 分类 | UX、发言恢复 |
| 证据 | [speech-step-4-text-fallback.png](browser-room-control-dogfood-20260722/screenshots/speech-step-4-text-fallback.png)、[joiner-text-fallback-open.png](browser-room-control-dogfood-20260722/screenshots/joiner-text-fallback-open.png) |

点击“改用文字完成本轮发言”后，页面立即把状态改为“正在发言”，但文本框为空、计时继续消耗；在控制权冲突时文本框还会直接 disabled。用户可能只是查看备用方案，却已经占用了一轮。

**建议**

先显示“确认使用文字完成本轮”并完成席位接管，确认后再启动本轮计时；输入框应在首屏获得焦点，明确显示“提交后结束本轮”。若无法接管，直接展示接管按钮和恢复原因。

## 观测到的浏览器错误与网络情况

- JavaScript exception：本次流程未发现未处理异常。
- 失败请求：`404 GET /api/rooms/search?code=000000` 对应无效房间搜索，页面正确显示“没有找到房间 #000000”，可接受；`409 POST /api/rooms/264011/control-lease` 是高影响控制权冲突。
- LiveKit：多次连接/断开和不同 device_id；浏览器自动播放策略产生 `NotAllowedError` 警告，页面提供“播放比赛声音”按钮。
- HAR 共记录 234 个请求，已保存用于后续对比。

## 后续修复验收顺序

1. 先修复 ISSUE-001：使用两个真实浏览器和同一席位验证接管、旧页只读、发言不会因 409 超时；连续重复至少 3 次。
2. 修复 ISSUE-002：从首页卡片、观战页、控制台都能在不改 URL 的情况下回到正确角色页面。
3. 用干净账号和干净房间重跑 1v1 双人完整比赛两次，确保首轮、自由辩论、总结都能提交，结果页发言数与实际提交数一致。
4. 再跑 4v4：两名真人 + 六个 AI 空席，检查 AI 补位、真人控制权和公开观战脱敏。
5. 最后处理状态文案、连接复用和移动端精修；每次修复后保留一份新的 HAR、截图和结果页。
