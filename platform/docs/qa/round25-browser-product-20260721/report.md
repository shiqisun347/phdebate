## ISSUE-001：输入不存在的房间号后静默失败

| 字段 | 内容 |
|---|---|
| 严重度 | Medium |
| 分类 | 功能 / 错误恢复 / UX |
| 页面 | `/` 的“搜索房间”参赛窗口 |
| 复现视频 | [issue-001-invalid-room.webm](videos/issue-001-invalid-room.webm) |

输入格式正确但不存在的六位房间号 `000000` 后点击“进入房间”，请求返回 404，但页面既不跳转，也不显示“房间不存在/已结束/请核对房间号”等反馈；按钮恢复原状，用户只能猜测是否点击成功。在学生集中参赛时，这会产生重复点击、反复询问组织者和误判系统卡顿。

复现：

1. 登录后从首页打开“创建 4v4 比赛”，切换到“搜索房间”。
   ![打开搜索房间](screenshots/issue-001-step-1.png)
2. 输入 `000000`。
   ![输入不存在的房间号](screenshots/issue-001-step-2.png)
3. 点击“进入房间”，等待 3 秒，界面没有任何错误反馈。
   ![静默失败结果](screenshots/issue-001-result.png)

网络证据：`GET /api/rooms/search?code=000000` 返回 404，浏览器控制台无异常，说明失败被前端吞掉，而非网络未发送。

建议：在输入框下方显示持久、可读屏的行内错误；区分“不存在”“已关闭”“不属于当前赛事”“服务暂不可用”；失败后保持输入和焦点，提供“重新查询”而不是让用户重走参赛窗口。

## ISSUE-002：赛果页时间线容器产生数屏无效空白

| 字段 | 内容 |
|---|---|
| 严重度 | Medium |
| 分类 | 视觉 / 响应式 / UX |
| 页面 | `/rooms/269177/result` |
| 复现视频 | N/A（页面加载即出现） |

公开赛果页显示“已加载 25/25”，实际时间线事件只占容器上部，容器仍被拉到极高高度。桌面端留下约两屏空白，390px 手机端留下更多无意义滚动距离，用户很难判断页面是否还有内容，也显著削弱赛后复盘体验。

- [桌面完整截图](screenshots/ended-result-anonymous-desktop.png)
- [手机完整截图](screenshots/ended-watch-anonymous-mobile-after5s.png)

建议：容器高度由事件内容自然撑开；若使用虚拟列表，应按真实项目数量计算高度；匿名投影被裁剪后不能沿用完整事件数对应的占位高度。移动端可默认折叠为关键节点，并提供“展开全部事件”。

## ISSUE-003：新用户无历史比赛时仍显示“第 1 / 1 页”

| 字段 | 内容 |
|---|---|
| 严重度 | Low |
| 分类 | 内容 / 状态一致性 |
| 页面 | `/me` |
| 复现视频 | N/A（空状态加载即出现） |

新注册用户历史比赛为 0，卡片同时显示空状态和“第 1 / 1 页”。这会让用户误以为存在一页未加载出来的数据，也降低档案页的可信度。

![空历史仍显示页码](screenshots/me-mobile-full.png)

建议：总数为 0 时隐藏分页和页码；只有记录数超过单页容量时才显示分页控件。

## ISSUE-004：长期暂停房间未提示故障是否已经恢复

| 字段 | 内容 |
|---|---|
| 严重度 | Medium |
| 分类 | 运维 UX / 错误恢复 |
| 页面 | `/rooms/117519/control` |
| 复现视频 | N/A（状态加载即出现） |

房间控制台持续显示历史原因“没有可用且已暖机的 MOSS-TTS-Realtime endpoint”，并提供“重试异常步骤”，但没有呈现当前依赖服务是否已恢复，也没有给出“当前已满足重试条件/仍不建议重试”的决策提示。与此同时系统总览明确显示 MOSS 正常。管理员必须跨页面比对并自行推断，容易在服务仍异常时反复重试，或在服务恢复后长期遗忘暂停比赛。

- [暂停房间控制台](screenshots/control-paused-desktop.png)
- [同一时刻系统总览显示服务正常](screenshots/admin-desktop-full.png)

建议：在异常卡片内并列显示“历史故障”和“当前依赖健康”；服务恢复时显示绿色“故障条件已解除，可以重试”及最近健康检查时间；仍异常时禁用重试并解释原因。比赛监管列表可增加“已恢复、待人工重试”筛选与计数。

## ISSUE-005：后台用户与比赛列表一次渲染过多行和操作

| 字段 | 内容 |
|---|---|
| 严重度 | Medium |
| 分类 | 信息架构 / 性能 / 可操作性 |
| 页面 | `/admin` 的用户管理与比赛监管 |
| 复现视频 | N/A（列表加载即出现） |

用户管理第一页一次展示约 50 名用户，每行同时暴露重置密码、QA 标记、停用、管理员授权四个高风险操作；无状态筛选、角色筛选、数据类型筛选或批量处理入口。可访问树已超过 500 个交互引用。比赛监管同样把大量历史 QA 与正式比赛堆在单页。当前仅 51 名注册用户时已经需要长距离滚动，无法支撑后续大量学生与比赛数据。

- [用户管理完整截图](screenshots/admin-users.png)
- [比赛监管完整截图](screenshots/admin-match-supervision.png)

建议：默认每页 20–25 条；加入角色、账号状态、正式/QA、最近活跃时间筛选；默认收起低频操作到行级菜单，保留一个主操作；支持选中 QA 账号后批量停用/归档；记住筛选条件并在列表顶部显示总数和当前范围。
