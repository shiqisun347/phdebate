## 结论

1. 原生流式输出确实能把单路“等待完整 WAV”约 4.0 秒缩短为约 1.2 秒收到第一块 PCM，因此值得接入浏览器流式播放；但当前单路首块 P95 仍高于 0.9 秒目标，且首块通常已经是 32–61 KiB，不是极小低延迟帧。
2. 当前生产配置下并发请求基本串行：两路中的第二路首块约 5.7–6.4 秒，三路中的第三路约 9.9–11.3 秒。服务虽然没有报错，但这不等于 2–3 场实时可用。
3. 并发 2/3 的总体 RTF P95 分别为 1.795/2.651，明显超过实时阈值；只把应用改成 `stream=true` 不能关闭容量问题。
4. 单请求块间最大空洞 P95 约 0.86–0.91 秒。浏览器端必须使用带 PTS 的固定大小 PCM 帧、AudioWorklet 环形缓冲和欠载统计，不能把 HTTP transport chunk 直接当播放帧。
5. 下一步应在独立灰度实例把 `running_max_req_size` 提升到 2，配合真实流式客户端测 TTFT、RTF、GPU 水位和第三路公平等待；通过后才允许生产 `2 active + 1 bounded waiting`。当前生产并发设置保持不变。
