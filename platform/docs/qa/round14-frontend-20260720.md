# Round 14 Web 产品、视觉与性能审计

日期：2026-07-20
范围：首页、赛事详情、参赛弹窗、房间大厅、个人中心、排行榜、系统管理后台。
硬边界：未修改 `DebateStage`、LiveKit、AudioWorklet、PCM、MOSS、TTS、ASR。

## 结论

当前 Web 已形成清晰的“赛事大厅 → 赛事详情 → 创建/加入房间 → 大厅准备 → 比赛 → 结果/历史”主线。视觉不是通用模板：正反方双色语义、六位房间号、席位状态、稷下“辩”字标识构成稳定识别系统；深色底、克制的紫青强调色、紧凑信息卡和明确主按钮，适合学生高频参赛，也接近字节系成熟产品强调的高信息密度、清晰反馈和低学习成本。

本轮发现并修复 3 个有直接证据的问题：

1. 排行榜首屏此前并行请求未携带 `season_slug`，但却把结果标记为“已加载指定赛季”。赛季切换或新旧赛季交接期间，页面可能显示错误榜单且不再发起正确请求。
2. 大厅“锁定席位并开始”确认框只拦截键盘 Tab；脚本、辅助技术或程序化聚焦仍可把焦点移回背景，破坏模态语义。
3. Admin 身份验证和首屏载入仍使用无 `role=status` 的纯文本 loading，和其他页面已经统一的可访问加载组件不一致。

## 已实施修复

### 排行榜数据正确性

- 赛事目录与赛季目录继续通过 `Promise.all` 并行获取。
- 等两项依赖确定后，再请求同时带 `competition_slug`、`season_slug` 的权威榜单。
- 不再用后端默认赛季响应冒充用户当前选择的赛季。
- 保留请求序号与 key 去重，快速切换时旧响应不能覆盖新选择。
- 测试明确断言请求为：
  `/api/rankings?competition_slug=daily-4v4&season_slug=season-1`。

这是一次有意的依赖式请求：榜单参数依赖目录返回的正式赛与赛季，不能为了表面并行而牺牲数据正确性。若后续需要进一步压缩首屏时延，应新增服务端聚合接口，而不是恢复无赛季参数的预热请求。

### 开赛确认框

- 新增 `focusin` containment；焦点从任何路径离开确认框时，立即回到第一个可操作按钮。
- 点击遮罩可安全返回检查，并把焦点还给“锁定席位并开始”。
- 操作正在提交时禁止遮罩关闭，避免用户误以为开始请求已取消。
- 保留 Escape、正反向 Tab 循环、body 滚动锁和关闭后的焦点恢复。
- 新增自动化测试覆盖背景程序化聚焦、遮罩关闭与焦点恢复。

### Admin 加载反馈

- Admin 身份验证和系统数据载入统一使用 `PageLoading`。
- `PageLoading` 增加可选上下文说明：普通页面默认“正在同步最新比赛数据”，Admin 分别显示“正在核对账号权限”和“正在同步服务状态与比赛数据”。
- 加载状态具备 `role=status`、`aria-live=polite`、`aria-busy=true`。

## 逐项审计

### 信息层级与文案

- 首页主任务是创建正式 4v4 比赛，主按钮位置、语义和视觉权重正确；排行榜是次操作。
- 赛事卡明确展示席位数、计分属性、赛季开放状态、可观战场次，创建受阻时文案会切换为“加入已有房间”。
- 参赛弹窗把“创建”和“搜索房间”作为互斥选择，创建时只要求辩题与本人席位，符合空席由 AI 补齐的产品规则。
- 大厅同时显示真人准备数、真人在线数和 AI 补位数；开赛前再次总结真人/AI 数量及不可逆影响。
- 个人中心把“继续比赛”“积分变化”“历史记录”“账号安全”分区，终局缺失胜方时显示“结果未记录”，不会伪造结果。
- 排行榜空态解释如何产生记录，不是无方向的空白页。
- Admin 使用按领域拆分的 9 个模块，移动端切换为下拉选择，不把桌面侧栏硬塞入窄屏。

### 视觉与响应式

- 颜色 token 集中在 `globals.css`，紫色用于品牌/主操作，青色用于交互焦点，绿色/黄色/红色用于成功、注意与危险，语义稳定。
- 首页只在“辩”字轨道装置使用强视觉记忆点，其他区域保持克制，符合“一处签名元素”的设计原则。
- 赛事卡、信息面板、表单控件和按钮圆角/边框/阴影一致；没有混入另一套浅色后台模板。
- 560px 以下，赛事卡、参赛方式、席位选择、表单与历史记录均切为单列或移动卡片。
- 所有主要按钮具备不低于约 44px 的触控高度；键盘焦点使用高对比青色轮廓。
- 已提供 `prefers-reduced-motion` 降级；长逐字稿、时间线和历史比赛项目使用 `content-visibility:auto`。

### 加载、错误与空态

- 首页核心赛事先返回，公开比赛和排行榜失败或缓慢时不会阻塞创建比赛。
- 公开比赛只在页面可见时每 15 秒刷新，并有 in-flight 防重复；后台标签页不继续轮询。
- 首页、赛事详情、个人中心、排行榜、房间页和 Admin 均有可重试错误或明确加载状态。
- 公开比赛/排行榜二级数据失败时保留最近一次成功结果，并明确说明不影响参赛。
- 大厅对“网络写入结果未知”和“实时连接已恢复但操作尚未确认”分别提示，允许沿用幂等键安全重试。

### React / Next 性能

- 首页次级请求不制造首屏瀑布，公开比赛请求有并发锁。
- `useSession` 已合并同页并发会话请求。
- Admin 非首屏模块和编辑弹窗使用 `next/dynamic`，生产构建确认模块被拆入独立 chunk；切换模块后才加载其数据。
- Admin 同模块请求使用 pending map 去重，独立请求使用 `Promise.all`。
- 排行榜、赛事详情、个人中心用 sequence 防止旧请求覆盖新状态。
- 结果页与历史长列表已有浏览器渲染跳过优化；当前赛事和大厅席位数有明确上限，不需要引入虚拟列表的额外复杂度。

### 退役域与可安全删除代码

运行 Web 源码中未发现教师、老师、课堂、课程、班级、全班或教学活动文案。保留的两类命中均不属于产品遗留：

- E2E 中保留退役路由反向测试，持续保证 `/teacher`、`/teacher/consents`、`/admin/classrooms` 返回 404。
- 冻结的 LiveKit 文件中有一条描述网络余量的英文注释；根据音频保护边界不修改。

未发现可在不影响行为、测试或受保护语音链路的前提下继续删除的 Web 模块。Admin 已完成动态模块化；再次机械拆分只会增加跨文件状态传递和维护成本。

## 后续建议（本轮不冒险实施）

- 若生产数据量使 Admin 用户/房间列表超过目前分页规模，优先做服务端游标分页和查询索引，不在客户端一次性载入后再筛选。
- 若排行榜首屏时延成为真实瓶颈，应增加“赛事 + 当前赛季 + 榜单”聚合读取接口或服务端缓存，以一次权威请求消除依赖等待。
- 可在下一轮真实浏览器视觉验收中固定采集 390×844、1366×768、1920×1080 三组截图，重点比较首页首屏、参赛弹窗最大内容高度、8 席大厅和 Admin 密集表格；任何发现仍应限定为非音频区域。
