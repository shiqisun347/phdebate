## 结论

核心的“注册 → 建房 → 第二位真人加入 → 认领席位 → 准备 → 断网恢复 → 房主关闭房间”链路可以完成。跨浏览器的席位、准备状态和真人数量能实时同步；重复注册提交、重复抢座和重复准备没有造成重复用户、重复席位或状态翻转。错误房间、已关闭房间和越权控制台均未泄露控制能力。

## 问题

### ISSUE-001：未公开的等待房间仍可被匿名枚举并查看真人姓名

| 字段 | 内容 |
|---|---|
| 严重度 | Medium |
| 分类 | 隐私 / 产品设计 |
| 页面 | `/rooms/:code/lobby`、`/rooms/:code/watch` |

**现象**

房间 `100561` 尚未开始，也没有出现在首页“公开比赛”列表中，但未登录浏览器直接访问大厅或观战地址，可以看到辩题、房主真实姓名、另一位真人姓名、具体席位和准备状态。不存在的六位房间号会返回明确的“房间不存在”，因此六位码同时承担资源编号和低熵访问凭证，存在自动化枚举空间。

**复现步骤**

1. 登录用户创建一个尚未开始的 4v4 房间。
2. 确认首页公开比赛列表仍为 0 场。
3. 使用无 Cookie 的匿名浏览器打开 `/rooms/{roomCode}/lobby`。
4. 匿名页面完整显示两名真人的真实姓名、阵营、辩位和准备状态。
5. 访问一个不存在的六位码，页面返回可区分的“不存在”结果。

**建议**

- 明确区分 `public`、`unlisted`、`private` 三种可见性。
- 等待阶段默认至少要求登录；匿名观战只对明确公开且已开始的比赛开放。
- 房间号只用于查找，分享链接附带不可枚举的高熵邀请 token；服务端对房间搜索设置速率限制和审计。
- 如果产品坚持所有比赛公开，应在建房前明确告知真实姓名将公开展示，避免学生误解。

### ISSUE-002：创建房间默认选中首席位，但选择状态未提供语义，也允许用户未经确认直接创建

| 字段 | 内容 |
|---|---|
| 严重度 | Medium |
| 分类 | UX / 无障碍 / 数据准确性 |
| 页面 | 首页“创建比赛”弹窗 |

**现象**

4v4 和 1v1 建房弹窗会视觉默认选中“正方1辩”，创建按钮立即可用。用户未主动选择任何席位直接点击创建，系统就把用户写入正方1辩。本轮房间 `100561` 即通过这种方式创建。辅助功能树中的席位按钮没有 `aria-pressed`、选中说明或单选组语义，屏幕阅读器无法得知哪个位置已被选中。

这会让不熟悉界面的学生误以为尚未选席，或在未意识到默认值的情况下以错误辩位参赛；辩位属于比赛关键数据，开赛后纠正成本较高。

**建议**

- 首次建房不默认选席，必须由用户明确选择后才启用创建；或至少在提交前显示“你将作为：正方1辩”的确认摘要。
- 使用 radio group，或给按钮增加 `aria-pressed` / `aria-checked` 及组标签。
- 创建成功页继续醒目标明姓名、阵营和辩位，并在锁房前允许一次明确的换位操作。

### ISSUE-003：错误房间页面把永久不存在描述成临时故障

| 字段 | 内容 |
|---|---|
| 严重度 | Low |
| 分类 | UX / 内容 / 无障碍 |
| 页面 | `/rooms/999999/lobby` |

**现象**

不存在的房间显示“页面暂时无法打开”，主要操作是“重新尝试”，但正文又说明“房间不存在或已被删除”。这是永久输入错误，不是临时网络故障；继续重试不能帮助用户。错误页主标题还是 `h2`，页面没有 `h1`。

**建议**

- 根据错误类型分别展示“房间号不存在”“房间已关闭”“服务暂时不可用”。
- 对不存在房间直接提供六位房间号输入框和“查找其他房间”，弱化无效重试。
- 错误页使用唯一 `h1`。

### ISSUE-004：非房主访问控制台被静默送到观战页

| 字段 | 内容 |
|---|---|
| 严重度 | Low |
| 分类 | UX / 权限反馈 |
| 页面 | `/rooms/100561/control` |

**现象**

普通参赛者和匿名用户访问控制台时，服务端权限隔离正确，但浏览器直接跳到 `/watch`，没有说明“仅房主或管理员可进入”。从别人分享的链接进入时，用户会以为控制台加载错了或按钮丢失。

**建议**

重定向后显示一次明确且不泄露后台信息的提示：“你没有本房间控制权限，已切换为只读观战”。

### ISSUE-005：390px 移动端导航按钮触控区域为 42×42px

| 字段 | 内容 |
|---|---|
| 严重度 | Low |
| 分类 | 移动端 / 无障碍 |
| 页面 | 移动端全局头部 |

**现象**

390×844 视口中，导航菜单按钮的实际可见触控区域为 `42×42px`，低于常用的 44px 最小触控目标。页面没有横向溢出，其他主要操作尺寸正常。

**建议**

将菜单按钮的最小尺寸统一到 `44×44px`，并保证按钮之间至少有 8px 间距。

## 已通过的真实场景

### 匿名与公开页面

- 首页赛事数量、公开比赛数量和赛事详情数据一致，当前均为 0 场。
- 4v4、1v1 赛事详情、题库、规则、排行榜和观战空状态均可读取。
- 四个赛事详情标签可切换，选中状态和 tabpanel 语义正确。
- 全局排行榜和赛事排行榜均有清楚的空状态。
- 匿名搜索不存在房间返回明确错误；已关闭房间不会继续进入大厅或观战。

### 注册、登录和个人中心

- 必填项由浏览器约束；两次密码不一致会显示字段级错误。
- 注册按钮双击只创建一个账号并登录。
- 错误密码返回统一的“账号或密码错误”，没有泄露账号是否存在。
- 正确登录双击不会产生异常会话。
- 空个人中心、进行中比赛入口、浏览器前进/后退和退出登录均正常。
- 进行中房间关闭后，个人中心“进行中”从 1 回到 0。

### 4v4 双真人大厅

- 房主创建房间后，第二个独立登录用户可以访问并认领对方席位。
- 双击空席只认领一次，没有出现重复席位或人数错误。
- 双击“确认准备”后状态保持“已准备”，没有被第二次请求反向取消。
- 房主浏览器实时收到第二位真人加入和准备状态。
- 非房主无法进入控制台，所有应急操作均未暴露。
- 房主关闭房间前有确认；取消确认不会关闭，确认后双方都无法再次进入。

### 弱网与恢复

- 真人浏览器断网并刷新时出现浏览器原生离线页。
- 网络恢复后重新打开同一大厅，账号、席位和准备状态均恢复，没有重复认领或丢失。

### 390×844 移动端

- 首页、赛事详情、大厅和个人中心均无横向溢出，`scrollWidth = innerWidth = 390`。
- 赛事标签为单行，单个标签高度 50px，没有上轮发现的换行问题。
- 大厅席位、房间号、准备/释放操作和个人中心卡片均保持可读。
- 移动导航支持 Escape 关闭，弹窗打开后焦点进入关闭按钮，Shift+Tab 在弹窗内循环，关闭后焦点返回触发按钮。

### 性能与控制台

- 首页一次实测：TTFB 31.2ms、FCP 108ms、LCP 224ms、CLS 0.06。
- 普通大厅、赛事、登录、个人中心页面未观察到 JavaScript 异常或 5xx 请求。
- 测试工具启用域名隔离后会主动禁用 WebRTC；观战页因此出现的兼容播放提示属于测试容器行为，未作为产品缺陷，也未继续测试音频。
