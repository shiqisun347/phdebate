# Round 10 后端多人比赛可靠性审计

日期：2026-07-20
范围：平台 API、比赛引擎、排行榜投影、比赛归档稳定性
明确排除：TTS、MOSS、LiveKit、AudioWorklet、PCM、浏览器播放实现

## 结论

本轮针对大量学生同时使用的高风险路径进行了代码审计和可执行场景验证。新增 9 个 Round 10 场景测试，并完成全量 API 回归。重点修复了三个会影响正式比赛可信度或学生隐私的问题：

1. 管理员停用账号后，虽然会话会失效，但真人席位此前仍可能保持在线、占位或继续持有房主控制权。
2. 比赛已经明确终止后，状态为 `timed_out` 的真人发言仍可迟到提交，导致终止时生成的归档与后续历史页面不一致。
3. 未开赛的公开等待大厅虽不出现在公开列表中，但匿名用户凭六位房间号仍可读取真人姓名、席位和准备状态。

修复后，全量 API 测试为 **403 passed**。

## 已实现改进

### 1. 停用账号后的房间自动修复

比赛引擎现在在每次权威房间处理时重新检查真人席位对应的账号状态，不依赖浏览器主动断开，也不等待正常的 60/120 秒离线超时。

- 大厅中的停用账号：立即释放席位。
- 进行中、准备中、暂停中或裁判中的停用账号：立即切换为 `ai_substitute`。
- 停用账号正在真人发言：权威 Speech 状态改为 `interrupted`，原因记录为 `account_disabled`。
- 停用账号是房主：优先将控制权移交给在线、有效的真人辩手。
- 账号停用产生独立审计原因：`owner_account_disabled`、`account_disabled`，可与普通网络超时区分。
- 原有会话撤销逻辑保持不变，HTTP、房间 WebSocket 和 ASR WebSocket 均不能继续使用已撤销身份。

若房间里没有其他在线有效真人，系统不会把控制权错误地交给 AI 或停用账号；系统管理员仍可从全局后台处理该房间。

在线真人优先获得房主权限；如果其他有效真人只是暂时离线，控制权会绑定到其中一人，使其返回后能够接管，而不会永远卡在已停用的旧房主名下。

### 2. 连续房主移交链

新增完整场景：

`房主 A 主动移交给 B → B 被管理员停用 → 引擎将控制权移交给在线 C`

验证结果：

- 只产生两条权威 `room.owner_transferred` 事件。
- 事件顺序、前后 owner ID 和原因均正确。
- 被停用 B 的大厅席位被释放。
- 最终只有 C 获得房主修复权限。

### 3. 公开排行榜的停用账号隔离

公开排行榜现在同时排除：

- 测试账号；
- 已停用账号。

停用不会删除 `LeaderboardEntry` 或追加式 `RatingChange` 历史。管理员仍可查看完整记录；账号恢复后，原成绩重新进入公开排行榜，不会重复结算或丢分。

### 4. 终止后的迟到发言写保护

`POST /api/rooms/:code/speech/finish` 现在遵循以下边界：

- 正常阶段推进后，`timed_out` 发言仍可按既有设计迟到补交。
- 房间进入 `terminated` 或 `cancelled` 后，不再允许补交新发言内容。
- 已带相同幂等键成功提交过的请求仍可返回原结果，不重复写入。

这样可保证显式终止时的事件、逐字稿、结果页和归档保持一致。

### 5. 等待大厅的匿名隐私边界

六位房间号现在只作为定位信息，不再被当作匿名访问凭证：

- `public + lobby`：匿名 REST、RTC token 和房间 WebSocket 均不能读取；登录用户仍可搜索房间、查看席位并正常认领。
- `private`：匿名用户仍被拒绝，非成员登录用户也仍被拒绝。
- `public + 已开始/已结束`：继续支持匿名观战和结果查看。
- 公开快照缓存与 REST 权限使用同一组状态常量，避免 WebSocket 绕过 REST 边界。

匿名访问者因此无法在开赛前通过遍历六位房间号批量收集学生真实姓名、辩位和准备状态；开赛后只有明确设置为公开的比赛才进入观战投影。

## 新增验证场景

文件：`apps/api/tests/test_round10_engine_scenarios.py`

1. 4v4 房间中 3 名学生并发认领不同席位，与房主组成 4 名真人。
2. 4 名真人并发准备，重复点击准备只视为重放，不增加事件。
3. 同一房主的两个并发开始请求只创建一个 Match、一个 `room.locked` 事件，并只执行一次 AI 补位。
4. 大厅房主被停用后，会话立即撤销，席位无需等待 120 秒即释放，并移交控制权。
5. 进行中真人被停用后，正在发言被中断、席位由 AI 接替，旧会话不能申请恢复。
6. A→B→C 连续房主移交链保持唯一、顺序正确。
7. 停用账号从公开榜隐藏但历史积分保留，恢复账号后成绩重新出现。
8. 终止比赛后，准备、认领、移交、暂停、开始发言和迟到完成发言均不能改变房间序列。
9. 上述失败写请求前后重新构建归档，`sha256` 和 `source_sha256` 保持一致。
10. 关闭大厅后，陈旧页面不能通过准备、开始、认领或移交操作复活房间；重复关闭为无副作用重放。
11. 匿名用户不能读取公开等待大厅、私密等待大厅、RTC token 或房间 WebSocket；登录用户按房间号加入公开大厅仍正常。
12. 公开房间开始后，匿名观战投影恢复可用，并显示正式比赛选手信息。

## 设计边界与后续建议

- 停用账号后的席位修复由权威 Match Engine tick 执行，通常在数秒内完成；会话权限在管理员提交停用事务后立即失效。
- 如果 Match Engine 本身不可用，会话仍然安全失效，但席位投影要等待 Engine 恢复。系统健康页应继续把 Engine 故障作为阻止正式开赛的严重异常。
- 本轮没有修改任何语音合成、实时音频传输或浏览器播放代码，也没有改变当前可靠语音基线。
- 大规模正式使用前仍建议在 PostgreSQL/Redis 生产拓扑中执行一次 8 真人、多人多设备、管理员实时封禁和连续房主移交的压力演练；SQLite 单元测试证明业务不变量，但不替代生产锁等待和网络故障注入。
