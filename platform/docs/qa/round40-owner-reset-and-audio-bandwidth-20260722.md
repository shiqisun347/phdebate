# Round 40：房主重置与音频带宽评估

日期：2026-07-22

## 结论

- 比赛音频继续只保留一条连续的 LiveKit `agent-tts` WebRTC 音轨。
- WebRTC 发布端为单声道 Opus，最大码率 64 kbps，并保留 RED 抗丢包；浏览器不接收 WAV/MP3 分片，也不创建多个播放器。
- 64 kbps 只影响传输量，不会降低 MOSS-TTS-Realtime 的模型推理 RTF。24 kHz 单声道原始 PCM 约为 384 kbps，LiveKit 已经将它压到约六分之一；以总计不超过 5 个观众计算，带宽不是当前 RTF 或首音延迟的主要瓶颈。
- 房主现在可以在 AI 发言进行中显式“重置当前发言”。系统会取消 LLM/TTS、清空服务端 LiveKit 队列和浏览器待播样本，并在同一音轨上重新合成；已固定文字会复用，不会切换播放器。

## 验证

- 本机房主重置测试：通过。旧尝试状态从 `reset_requested` 收敛为终态 `reset_retried`；文字已经固定时，新发言复用相同文字且不再次调用 Agent。用户结果和历史分页只展示真正完成的发言，重置尝试保留在审计事件中。
- 浏览器控制台：新版运行中的 AI 发言显示“重置当前发言”，确认对话框明确说明同一条 WebRTC 音轨、清空队列和不切换播放器。
- 生产房主重置完整赛：房间 `399616` 通过。正方真人立论后，反方 AI 首次开始实际播放，房主执行 `reset_ai_speech`，同阶段重新建立一条权威 `agent-tts` 音轨并完成；随后自由辩论、双方总结和裁判全部完成。结果只包含 6 条有效发言，旧重置尝试没有污染赛后逐字稿。
- 1v1 人机完整流程：开场、固定阶段、自由辩论、总结、裁判均通过；AI 播放观察到 3/3；MOSS 结束后 active=0、orphan=0。
- 4v4 混合完整流程：11 个阶段、10 次发言、2 轮自由辩论、裁判完成；MOSS 结束后 active=0、orphan=0。

## 为什么暂不继续降音质

模型推理发生在“文本/音频 token → 声学 token → 解码器”路径中，浏览器收到的 Opus 压缩在推理完成之后。降采样或降低 WebRTC 码率不会让声学 token 生成更快，反而可能加重音色、清晰度和撕裂风险。DTX 也不适合连续辩论发言，可能造成短暂停顿和起音异常，因此保持关闭。

## 后续可做的 A/B 实验

1. 在不切换正式流量的独立 MOSS 进程中测试 FlashAttention 2。官方当前文档建议在支持的 GPU、`float16/bfloat16` 下使用，但 OpenMOSS issue #38 记录过 realtime + FlashAttention 2 的崩溃和短音问题，必须以 RTF、首音、完整音频和连续音轨回归作为准入条件。
2. 对 `decode_chunk_frames` 做 12/15/18 三档基准。增大块可能降低解码器调度开销，但会增加首音缓冲；只有在 RTF 改善且无 underrun、杂音、撕裂时才进入生产。
3. 评估 vLLM-Omni 的 MOSS-TTS-Realtime 适配。官方已提供 OpenAI 兼容接口，但当前平台必须保留“同一 TTS context 的 text-in + audio-out 双向流式”语义，不能直接用完整文本请求替换正式链路。

## 禁止事项

- 不使用 MP3/WAV 分片逐段 `audio.play()`。
- 不在一次发言中临时切换 PCM、HTMLAudio、WebSocket 和 WebRTC 播放器。
- 不为了追求带宽数字关闭 RED、降低到无法稳定传输的码率，或采用未经 A/B 验证的量化模型。
