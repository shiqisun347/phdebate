## 零、核心审计原则

1. **不要被清单限制。** 本文列出的用例是最低要求，不是测试边界。看到任何可疑、别扭、不完整或不符合用户预期的地方，都要继续探索。
2. **不要轻易判定 PASS。** 一个功能只有在“结果正确、反馈及时、操作可理解、错误可恢复、视觉可接受、权限安全、移动端可用”全部满足时才能 PASS。功能能完成但体验明显有问题，应至少记录 UX/PERF/VIS/A11Y 问题。
3. **区分问题类型。** 每个发现标记为：
   - `BUG`：实现结果错误或与产品规则冲突。
   - `GAP`：成熟产品应具备但当前缺失的能力。
   - `UX`：流程、操作逻辑、状态反馈或认知负担问题。
   - `VIS`：视觉层级、布局、审美、品牌一致性问题。
   - `PERF`：慢、卡顿、无响应、反馈延迟或资源加载问题。
   - `A11Y`：键盘、焦点、对比度、语义、触控尺寸等无障碍问题。
   - `CONTENT`：术语、文案、错误提示、信息表达问题。
   - `SECURITY`：权限、隐私、敏感信息或隔离问题。
4. **同时评价现有需求是否合理。** 不要因为“系统就是这样设计的”而忽略问题。若流程本身不符合用户目标，记录为产品设计缺陷并提出替代方案。
5. **以真实用户而不是开发者视角测试。** 不假设用户知道“Agent、SSE、Provider、ASR、TTS、状态机、Profile”等技术词语。
6. **以成熟产品标准审视。** 可参考 Lichess、Discord、Zoom、Google Meet、主流直播平台、赛事平台和大型 SaaS 后台的通用交互模式，但不要照搬界面。
7. **优先发现高影响问题。** 优先测试新用户首次使用、参赛主流程、比赛中断、发言权限、等待状态、结果可信度、多房间隔离和移动端。
8. **持续测试到问题趋于饱和。** 至少完成三轮探索：基础流程、异常/边界、产品体验。若第三轮仍持续发现新的 P0–P2 问题，应继续探索，而不是按清单结束。
9. **观察而不是脑补。** 所有结论都要有页面状态、操作结果、耗时、截图或明确的可复现证据。
10. **建议必须可开发、可验收。** 不要只写“优化 UI”“提升体验”，要说明修改什么、为什么、建议交互、优先级和验收条件。

## 一-A、产品使命与最终目标

本平台的核心目标不是展示一个技术 Demo，而是让大量参赛者围绕不同赛事低门槛、稳定、持续地开展真实辩论比赛，并完整收集可用于赛后复盘、能力评估和产品分析的辩论数据。产品信息架构只能围绕赛事、房间、比赛、选手、观众和比赛历史展开，不得新增学校、课程、班级、教师或教学活动专用流程。

你必须围绕以下结果评价和改进产品：

1. 参赛者第一次进入平台，不经过口头培训也能理解赛事、加入房间、准备、发言、恢复比赛和查看结果。
2. 房主和赛事运营者能快速发起比赛、掌握进行状态、发现异常、干预比赛并导出完整数据。
3. 多场比赛并发时，房间、席位、计时、字幕、音频、Agent、Judge 和 Memory 严格隔离。
4. 人类和 AI 辩手的发言顺序、权限、等待反馈和异常恢复足够可信，不会因不确定状态破坏比赛秩序。
5. 每场比赛都能形成可追溯的数据链：赛事、房间、用户、席位、阶段、发言、字幕、音频、时间戳、Agent 配置版本、裁判结果、积分和异常事件。
6. 数据采集必须完整、稳定、有身份关联，同时兼顾参赛者隐私、访问权限、保留周期、匿名化和导出审计。
7. 平台能支持多个赛事下连续多轮比赛，而不是每场比赛都依赖开发者或管理员临时救场。
8. 产品视觉和交互应让参赛者愿意使用、赛事运营者敢于大规模开放、观众能够理解比赛进程，而不是像内部运维工具。

建议持续关注并在报告中估算以下产品指标：

- 注册到成功参赛转化率。
- 创建房间到开赛的中位耗时。
- 比赛完整完成率和进入 `review_required` 的比例。
- 人类发言成功率、字幕完整率、音频播放成功率。
- 断线后 60 秒内恢复成功率。
- Agent、TTS、Judge 的典型与最慢可见延迟。
- 每场比赛数据完整度和可导出率。
- 房主或赛事运营者处理一场异常比赛所需步骤和时间。

## 四、严重程度定义

- `P0`：网站不可用、数据泄露、越权、跨房间串数据、不可逆数据破坏、比赛状态严重损坏。
- `P1`：注册登录、建房、参赛、自动比赛、Agent、TTS、裁判、结果页等核心流程无法完成；或设计导致大量用户无法理解、误操作、无法恢复。
- `P2`：局部功能错误、恢复能力不足、明显慢或卡顿、关键状态反馈缺失、严重响应式/可访问性/交互问题，但存在替代路径。
- `P3`：非阻塞的文案、对齐、视觉一致性、轻微易用性和体验精修问题。

同时记录两个额外维度：

- 用户影响：`全体用户 / 新用户 / 参赛者 / 观众 / 房主 / 管理员 / 移动端 / 辅助技术用户`。
- 发生概率：`高 / 中 / 低 / 未知`。

4. 退出登录，验证受保护页面失去权限；浏览器后退不应恢复可操作状态。
5. 重新登录后验证可以返回此前比赛。
6. 用第二浏览器或无痕窗口登录 User B，确保两个用户会话互不覆盖。
7. 普通用户直接访问 `/admin`、`/admin/agent-access` 和房主不属于自己的 `/rooms/:code/control`，必须被拒绝或跳转。

## 九、1v1 完整真实比赛

创建一个带 `QA-CU-1V1-时间` 标记的训练房间，并执行完整流程：

1. User A 创建 1v1 房间，填写自定义辩题，检查题目长度和特殊字符被安全转义。
2. 选择人类席位，验证姓名来自当前账号，不能冒用他人姓名。
3. 检查六位房间号、分享入口、席位图、准备状态和规则。
4. 测试未准备时开始比赛，必须被阻止并显示原因。
5. 准备后开始，确认空位自动变为 AI，席位锁定。
6. 人类回合：检查只有当前人类辩手的发言按钮可用；未轮到时按钮禁用且显示原因。
7. 测试麦克风权限、开始发言、结束发言、字幕区域、连接状态和剩余时间。不要录入敏感语音。
8. AI 回合：记录 Agent 等待状态、首个正文字符、MOSS 首个 PCM、浏览器真实首声、实时字幕、当前发言者和阶段自动推进。
9. 自由辩论：验证正反方轮换、单轮计时、已有发言者时按钮权限、提前结束后的轮次切换。
10. 总结阶段：验证双方顺序和内容显示。
11. 训练点评：验证 AI Judge 自动调用，返回胜方/平局、双方分、个人分和中文理由。
12. 结果页：验证时间线、逐字稿、结果、训练赛是否默认不计排行榜。
13. `/me` 中能找到并返回该比赛历史。

## 十、4v4 完整真实比赛

创建一个带 `QA-CU-4V4-时间` 标记的日常赛房间，至少覆盖：

1. User A 创建并认领一个人类席位。
2. 如果 User B 可用，让 User B 通过房间号加入并认领另一个空闲人类席位，验证并发抢同一席位时只有一人成功。
3. 两名用户分别准备；房主开始后其余席位由 AI 自动补齐。
4. 开场与规则预设语音正常播放。
5. 依次观察并记录：
   - 正方一辩立论
   - 反方一辩立论
   - 正方二辩驳论
   - 反方二辩驳论
   - 正方三辩质询
   - 反方三辩质询
   - 自由辩论至少正反方各两轮
   - 反方四辩总结
   - 正方四辩总结
   - AI 裁判评议
6. 每个阶段检查：阶段名称、当前席位、双方状态、计时、按钮权限、字幕、音频、自动推进和控制台时间线。
7. 记录所有 AI 辩手是否保持自己的姓名、人设和席位，没有把其他房间或其他辩手历史带入当前发言。
8. 结果页验证队伍胜负、8 个席位个人分、判定理由、积分变化和排行榜更新。

如果完整流程需要较长时间，应持续等待并观察，不要因为单个 Agent 调用耗时 30–60 秒就提前判定失败；超过页面标示超时或 180 秒无进展再记录超时问题。

## 十一、多比赛、观战与权限隔离

1. 同时保留 1v1 和 4v4 两个不同房间，在不同标签页来回切换。
2. 确认 A 房间的题目、字幕、当前阶段、计时和发言不会出现在 B 房间。
3. 用未登录窗口访问 `/rooms/:code/watch`：可以观战，但没有麦克风、开始、暂停、跳过等按钮。
4. 匿名用户直接访问 `/rooms/:code/debate` 和 `/rooms/:code/control` 必须被拒绝。
5. User B 尝试操作 User A 的控制台必须被拒绝。
6. 同一账号在第二浏览器打开同一席位时，验证控制权接管机制；旧页面应转为只读，不能两个设备同时发言。
7. 使用错误房间号或另一个房间的 URL 参数，确认不会获得跨房间权限或数据。
8. 所有房间合计只允许 5 名观众；在不同房间凑满 5 名后，第 6 名观众必须收到明确的全站容量提示。辩手、房主和管理员不占观众名额。

## 十二、控制台和自动状态机

对本次测试创建的房间检查 `/rooms/:code/control`：

1. 阶段时间线、当前阶段、席位、Agent、ASR、MOSS-Realtime、LiveKit、Judge 和连接状态。
2. 暂停后计时停止，辩手按钮禁用；继续后从正确剩余时间恢复。
3. 页面刷新后暂停状态保持。
4. 在安全阶段测试“重试当前步骤”；不能产生重复发言或旧结果复活。
5. “跳过异常步骤”只对本次 QA 房间测试，并记录跳过后的阶段和历史是否一致。
6. 不要点击“终止比赛”，除非它是本次测试专门创建且已经无法继续的房间；点击前仍需按 Computer Use 规则请求确认。

## 十三、断线、刷新和恢复

1. AI 生成中刷新辩论页面，验证重连后仍显示正确阶段和任务状态。
2. TTS 播放中刷新，检查是否重复播放、丢失字幕或阶段提前推进。
3. 关闭比赛标签页后从 `/me` 返回比赛。
4. 临时切换到其他页面再返回，检查 WebSocket 自动重连提示。
5. 使用第二浏览器接管后再刷新旧页面，确认旧页面保持只读。
6. 若浏览器允许安全地模拟离线，短暂离线后恢复；否则标记 NOT-RUN，不要修改系统网络设置。

## 十四、主系统管理员后台

使用 System Admin 时默认只做只读检查和安全的连接测试；只有在已经确认问题根因、完成备份且修改属于本轮修复方案时，才通过受控方式保存配置变化：

1. `/admin` 导航、总览、用户、赛事、题库、赛季、自动流程、房间监管、裁判、服务健康和审计日志。
2. `/admin/agent-access` 只能看到 RESTful POST 接入方式，不应出现 SDK、Dify 或其他接入类型。
3. Agent Endpoint 应指向 `/debate/api/debate`，健康检查正常，密钥只显示“已配置”，不能看到明文。
4. 执行 Agent“测试连接”，记录状态和延迟，不点击保存。
5. 检查 AI 裁判配置已启用并指向 `/debate/api/judge`。
6. 检查进行中房间的 Agent、MOSS-Realtime、LiveKit、FunASR、Judge 状态。
7. 普通用户不能通过直接 URL、浏览器后退或修改前端路由进入后台。

## 十六、桌面和手机视觉验收

## 十七、内容与安全检查

1. 自定义辩题输入 `<b>QA-CU</b>` 等无害 HTML 字符，页面必须以文本显示，不能作为 HTML 执行。
2. 输入超长题目、前后空格和重复空格，验证限制与规范化。

## 十七-A、用户角色与真实任务审计

至少分别以以下角色完整走查，不要只换账号不换思考方式：

1. **第一次使用的参赛者**：不知道辩论流程、不理解技术术语、可能害怕开启麦克风。
2. **有经验的辩手**：关心规则、发言顺序、计时精确性、对手历史和复盘质量。
3. **房主/队长**：关心如何邀请、确认到场、解决未准备、处理掉线和开始比赛。
4. **匿名观众**：关心现在进行到哪里、谁在说、双方观点、如何听声音和查看结果。
5. **赛事运营者**：关心赛事配置、开赛进度、异常房间、成绩、复核和数据导出。
6. **系统管理员**：关心服务健康、审计、异常恢复和不泄露技术配置。
7. **数据运营人员**：关心数据结构、完整性、匿名化、筛选、导出和可复现性。
8. **移动端和弱网络用户**：关心触控、屏幕空间、重连、音频和状态恢复。

对每个角色回答：

- 用户来这里最想完成什么？首页是否立即支持这个目标？
- 第一屏是否知道“这是什么、我能做什么、下一步是什么”？
- 哪一步最容易迷失、犹豫或犯错？
- 系统是否使用了用户不懂的内部术语？
- 用户失败后能否自己恢复，还是必须找管理员？
- 完成核心任务需要多少点击、多少页面、多少等待和多少记忆负担？
- 当前产品缺少什么，导致这个角色无法规模化使用？

## 十七-B、信息架构与交互逻辑审计

逐页审查并记录：

1. 页面是否有明确的主任务和唯一主按钮；是否多个按钮权重相同导致无法判断下一步。
2. 导航名称是否面向用户目标，而非数据库或技术模块。
3. 页面层级、返回路径、面包屑、浏览器后退和深链接是否一致。
4. 创建房间、搜索房间、加入比赛、观战的入口是否在用户预期位置。
5. 弹窗是否说明后果；关闭后是否保留输入；是否出现弹窗套弹窗。
6. 禁用按钮是否解释原因和解决办法，而不只是灰色不可点。
7. 点击后 100ms 内是否有视觉反馈；超过 300ms 是否出现明确 Loading；长任务是否显示阶段和预计等待。
8. 是否存在重复提交、连续点击、返回再提交造成的重复房间、重复发言或重复任务。
9. 成功、失败、警告、等待、暂停、断线、只读、已结束等状态是否视觉可区分。
10. 系统是否要求用户记住房间号、席位或上一页信息，而没有复制、分享和返回入口。
11. 错误信息是否回答“发生了什么、为什么、我现在能做什么”。
12. 操作是否符合现实辩论心智模型：准备 → 开赛 → 当前发言者 → 轮次 → 总结 → 裁判 → 结果。
13. 是否存在功能入口在不同页面重复但行为不一致。
14. 任何需要管理员介入的普通流程都要记录为可扩展性风险。

使用 Nielsen 十项可用性原则进行一次单独审计：系统状态可见性、现实世界匹配、用户控制与自由、一致性、错误预防、识别优于回忆、效率与灵活性、简洁设计、错误恢复、帮助与文档。

## 十七-C、视觉设计与审美审计

不要只检查错位。像成熟品牌和设计系统负责人一样评价：

1. 品牌气质是否统一，是否像面向参赛者的成熟辩论产品，而不是模板拼接或后台 Demo。
2. 字体层级、字号、字重、行高是否形成稳定的信息层级；正文是否过小或过密。
3. 间距是否有一致规律；卡片、表格、按钮、表单是否使用统一圆角、边框、阴影和留白。
4. 颜色是否过多、过艳、过暗；正反方颜色是否清楚但不依赖颜色作为唯一信息。
5. 主按钮、次按钮、危险按钮、文本按钮和禁用状态是否一致。
6. 图标是否风格统一、含义明确并配有必要文字。
7. 大屏舞台是否具有赛事氛围，同时保证题目、阶段、计时和字幕是视觉中心。
8. AI/人类、在线/离线、正在发言/等待、胜负等状态是否容易一眼识别。
9. Loading、空状态、错误状态、无比赛、无排名、无历史是否有专门设计，而不是空白区域。
10. 动效是否帮助理解状态变化；是否过度、突兀、卡顿或引起视觉干扰。
11. 桌面端是否有效利用宽屏，移动端是否避免拥挤和信息丢失。
12. 截图每个核心页面后，以 1–5 分评价：专业感、清晰度、一致性、情绪价值、可读性。

对视觉问题不要只写“难看”。说明具体元素、视觉原则、用户影响、建议布局和可验收标准。

## 十七-D、性能、卡顿与等待体验

对核心页面和核心动作至少重复 3 次，记录可见耗时和体感：

1. 首次打开和二次打开首页、赛事页、房间页、后台、Agent 后台。
2. 登录、创建房间、搜索房间、准备、开始、暂停、继续、页面刷新和返回比赛。
3. Agent 从进入准备状态到出现首个文字、生成结束、TTS 开始、TTS 结束。
4. Judge 从进入评议到结果页可见。
5. WebSocket 断开到重连、刷新到恢复正确状态。
6. 长列表滚动、后台 Tab 快速切换、多个比赛标签页切换时是否掉帧或冻结。
7. 快速连续点击按钮时页面是否重复请求、卡死或状态抖动。
8. Loading 时是否仍可误触其他操作；是否存在长时间无任何反馈。
9. 图片、字体、音频和 JavaScript 是否重复加载或明显阻塞页面。
10. 记录最快、典型、最慢值；无法精确计时也要用秒表或可见时间粗测。

建议体验阈值：

- 点击反馈：100ms 内。
- 普通页面可操作：2 秒内较好，超过 4 秒记录问题。
- 普通保存/查询：1 秒内较好，超过 3 秒必须有清晰反馈。
- Agent 首字：理想 10 秒内；超过 20 秒需有明确进度；超过 60 秒属于严重体验风险。
- TTS 衔接：文字完成后 3 秒内开始较好；长空白必须解释。
- Judge：理想 15 秒内；超过 30 秒需展示评议进度。

不要仅因为后端最终成功就判定性能通过。用户不知道系统仍在工作时，等待本身就是产品缺陷。

并发和容量验证采用渐进方式，避免直接冲击生产：

1. 先验证 2 场真实比赛和多个观战标签页并行。
2. 再使用安全测试脚本验证 1、3、5 个隔离房间的状态创建、读取和 WebSocket 连接；第 6 个同时开放房间必须被服务端拒绝。
3. 将 5 名观众分散到多个房间验证全站共享名额，第 6 名观众必须被拒绝；释放任一名额后，新观众应能进入任意公开房间。
4. 记录并发增长时 API 延迟、错误率、Agent/TTS 排队、数据库连接、Redis、CPU、内存和日志异常。
5. 不得未经确认直接对生产发起 500 连接或高频压力测试。大规模压测优先在隔离环境完成；如果当前没有隔离环境，将其记录为工程缺口并提出建设方案。
6. 检查容量不足时用户是否看到排队位置、预计等待、降级说明和可恢复选项，而不是一直 Loading。

## 十七-E、功能完整性与产品缺口审计

主动判断平台为了支持“大量参赛者围绕不同赛事持续开展比赛并收集数据”还缺少什么。至少评估：

1. 新手引导、赛制示例、设备检查、麦克风试音、发言练习。
2. 赛事运营者配置赛事、题库、报名规则、候场与同时进行的房间。
3. 比赛预约、开始时间、到场提醒、未准备提醒和异常通知。
4. 房间邀请链接、二维码、复制反馈、分享权限和过期机制。
5. 赛事报名、候场、自动匹配、替补、迟到和缺席处理。
6. 按赛事实时总览：多少房间待开始、进行中、暂停、失败、待复核、已完成。
7. 批量暂停、延后、重新分组、恢复异常比赛和人工判定入口。
8. 参赛者赛前规则确认、数据采集告知、隐私说明和未成年人场景。
9. 逐字稿纠错、发言标记、精彩片段、赛事点评、个人复盘和同伴互评。
10. 结果分享、复盘、音频回放、时间线跳转、导出 PDF/CSV/JSON。
11. 数据筛选：赛事、参赛者、时间、题目、立场、席位、比赛状态。
12. 数据质量：缺失字幕、音频失败、重复发言、Agent 失败、Judge 待复核的标记。
13. 数据匿名化、保留周期、删除申请、访问审计和研究数据集版本。
14. 参赛者身份重复、重名、改名、账号找回和多设备使用。
15. 排行榜防刷、无效比赛、弃赛、管理员改判和积分补偿记录。
16. 举报、内容安全、人身攻击、违规发言和管理员处置。
17. 平台公告、帮助中心、常见问题、故障状态页和联系支持。
18. 大规模使用下的并发容量、排队提示、服务降级和公共网络不稳定方案。

每个缺口标记：目标用户、使用场景、当前替代办法、业务影响、建议 MVP、优先级、预计工作量 `S/M/L/XL`。

## 十七-F、数据采集与研究可用性审计

这是本项目核心目的，必须单独审计：

1. 确认用户、真实姓名、比赛、房间、席位和每段发言能稳定关联，同时内部使用不可变 ID 避免重名混淆。
2. 检查每个阶段是否记录开始/结束、发言者、阵营、角色、文本、音频、持续时间、状态和异常。
3. 检查人类 ASR 文本和 AI 原始文本能否区分；AI 模型、Prompt、参数版本能否追溯。
4. 检查中断、重试、跳过、超时、AI 接替和管理员干预是否进入事件日志。
5. 检查 Judge 原始结果、管理员复核和积分修正是否只追加而非覆盖历史。
6. 检查结果页展示的数据与导出/后台数据是否一致。
7. 检查数据缺失时是否明确标记，而不是静默使用空字符串或错误默认值。
8. 检查跨房间、跨比赛、跨参赛者的数据是否可能串联。
9. 评估赛事运营者和数据管理员能否按权限批量导出；如果没有，提出字段级导出方案。
10. 提出建议的数据完整度指标，例如每场比赛必须满足的必填事件和资源清单。
11. 评估数据采集告知、隐私、访问控制和匿名化是否足以支持大规模参赛场景。

报告中必须给出一份“建议数据字典”，至少列出实体、关键字段、用途、敏感级别、保留建议和质量规则。

## 十七-I、最低覆盖深度

4. 登录、建房、搜索房间、准备、开始、暂停/继续、返回比赛、Agent、TTS、Judge 至少重复 3 次观察稳定性。
5. 桌面和手机至少各完成一轮核心流程审计。

## 十七-J、ASR 与 MOSS-Realtime 语音质量专项

ASR 和 TTS 是核心比赛能力，不是附属功能。只要语音吞字、错字严重、停顿突兀、播放卡顿、音色廉价、等待过长、字幕与声音不同步或切换阶段错误，即使文本生成正确，也不能认为比赛体验合格。

必须把完整链路拆开测量：

`麦克风/测试音频 → AudioWorklet PCM 采集 → FunASR WebSocket → 临时字幕 → 最终字幕 → 发言记录 → Agent SSE 正文 delta → 稳定短语提交器 → 同一轮 MOSS 双向 WebSocket → 24 kHz PCM → LiveKit 48 kHz/Opus → 浏览器连续 AudioWorklet 播放 → 阶段推进`。

### J-1、标准语音测试语料

创建不含隐私信息的固定语料清单并保存到语音分析目录，至少覆盖：

1. 普通中文辩论句、短句、长句和多段落总结。
2. 逗号、句号、分号、冒号、问号、感叹号、引号、括号和破折号。
3. 人名和辩手名：陈思远、乾元、明川、知微、景行、若谷、清和、见山。
4. 数字、日期、时间、百分数、小数、序号、房间号和英文缩写。
5. 中英文混读：AI、LLM、GPT、API、ASR、MOSS-Realtime、WebSocket、LiveKit、Python。
6. 多音字和易错词，例如“行、重、长、乐、角色、数据、给予、质询、驳论”。
7. 连续相似音、重复词、快速绕口表达和句首/句尾短词，用于发现吞字、重复和截断。
8. 1 字、5 字、30 字、100 字、300 字和接近系统上限的文本。
9. Markdown 符号、URL、Emoji、项目符号和模型可能生成的特殊格式，验证播报前是否正确清洗。
10. 情绪与语气：客观立论、强势质询、快速自由辩论、沉稳总结；不能所有阶段都使用相同机械语调。

### J-2、MOSS-Realtime 音质与内容完整性

对每个实际启用的音色分别测试，不得只测默认音色。至少记录：

1. 文本是否完整播出，重点检查句首、句尾、分段边界、数字、英文和人名是否吞字、漏字、重复或错读。
2. 使用“原文本 → TTS 音频 → ASR 回转识别”计算字符错误率 CER，自动发现吞字和重复；同时人工试听，避免 ASR 自身错误掩盖音质问题。
3. 分段拼接是否出现突然停顿、异常长静音、单词被切开、重复半句、音量跳变、音色变化、爆音、点击声或波形断裂。
4. 语速、重音、停顿、语调、情绪和标点表达是否自然；质询、自由辩论和总结是否有合理差异。
5. 同一音色多次生成是否保持说话人稳定，不出现年龄、性别、口音和音高突然漂移。
6. 不同 AI 辩手是否容易区分；如果多人共享音色，用户是否仍能明确知道当前是谁在发言。
7. 长文本是否越到后面越快、越慢、变调、失真或丢失尾句。
8. 音量是否一致，切换音色或房间时不需要用户频繁调节音量。
9. 是否存在削波、底噪、电流声、过度降噪、齿音、金属音、混响和明显合成感。
10. 音频结束点是否准确；不能尾部保留很长静音，也不能最后一个字未结束就推进阶段。

为每条关键样本记录：

```md
| ID | 文本类型 | 音色 | 字数 | 合成耗时 | 音频时长 | RTF | 格式/采样率/码率 | CER | 吞字/重复 | 拼接间隙 | 卡顿 | MOS | 结论 |
|---|---|---|---:|---:|---:|---:|---|---:|---|---:|---|---:|---|
```

MOS 采用 1–5 分主观评分：自然度、清晰度、连贯性、音色舒适度、情绪适配度分别评分，并写出具体原因。至少由两个不同场景重复试听；不能只凭波形判断质量。

建议质量门槛：

- 标准清晰中文的 TTS→ASR 回转 CER 中位数不高于 5%，P95 不高于 10%。
- 固定标准语料中不得出现稳定复现的句首/句尾吞字、整词遗漏或重复句段。
- 人工试听综合 MOS 中位数至少 4.0/5，任何核心音色不应低于 3.5/5。
- 分段边界不应有明显可感知断裂；建议额外静音中位数低于 200ms，单次不超过 500ms。
- 音量差异建议控制在 3dB 内，避免削波；如工具可用，记录峰值、RMS/LUFS、静音比例和削波样本比例。
- 短文本合成并准备播放理想不超过 3 秒；长文本实时率 RTF 建议小于 0.8。

### J-3、TTS 实时性、传输与浏览器播放

使用浏览器 Network、服务日志和音频分析工具确认真实传输方式，不要假设一定是 WebSocket。如果当前是 HTTP WAV，明确记录；如果使用 WebSocket/流式帧，记录帧大小、频率和首帧时间。

必须检查：

1. Agent 首个可读正文字符、首个稳定短语提交、MOSS 首个非静音 PCM、LiveKit 首次 capture、浏览器真实首声的各段耗时。
2. 确认正文增量与音频输出均为同一轮双向流式；不得退化为等待完整 Agent 文本或完整 WAV 后播放。
3. 网络传输格式、Content-Type、采样率、位深、声道、Codec、码率、Content-Length 和实际传输字节。
4. 对比原始 PCM 理论大小和实际传输大小，计算压缩比；检查是否使用低效 Base64 或 JSON 包装音频。
5. 如果使用 WAV 导致移动网络下载大、首播慢，应评估 Opus/AAC 等浏览器兼容压缩方案，并同时验证压缩后音质和解码兼容性，不能只追求文件小。
6. 是否支持合理的缓存、Range 请求、断点读取；刷新后是否重复下载整段音频。
7. 浏览器缓冲是否充分，是否出现播放中断、音频饥饿、突然跳跃、重复、重叠或不同房间串音。
8. 弱网、高延迟、丢包和后台标签页恢复时的播放表现；无法使用网络模拟时标记 NOT-RUN 并提出测试环境方案。
9. 静音、音量、音频解锁、自动播放限制、蓝牙/耳机切换和手机扬声器场景。
10. 刷新、暂停、继续、跳过、重试和终止比赛后，旧 TTS 是否立即取消；禁止旧音频在新阶段“复活”。
11. 两场比赛同时产生语音时的队列、公平性、房间隔离、取消和 GPU/CPU 资源竞争。
12. 页面字幕与声音的同步：字幕不能提前很久消失，也不能在声音结束后长时间停留而阻塞阶段。

建议实时体验门槛：

- 文本完成到浏览器发声：短句 P50 ≤ 3 秒、P95 ≤ 6 秒。
- 播放期间非语义停顿或缓冲卡顿次数：标准网络下为 0。
- 同房间不得重叠播放两条发言；跨房间不得串音。
- 用户暂停/跳过后旧音频停止响应建议不超过 300ms。
- 阶段推进必须以实际播放完成或明确取消为准，不能只依据估算时长。

### J-4、FunASR 识别质量

通过浏览器真实麦克风和可重复的标准 WAV/WebSocket 测试两条路径。若 Computer Use 无法实际说话，使用经过授权的非敏感预录音或测试脚本发送标准音频，并明确区分“浏览器麦克风链路”和“服务端直接链路”。

至少测试：

1. 麦克风权限拒绝、允许、无设备、设备切换、静音设备和音量过低。
2. 开始录音前是否有设备检测、音量指示和试音入口；用户是否知道系统正在听。
3. 普通语速、快速自由辩论、慢速陈述、停顿、口头语、自我纠正和句中打断。
4. 男声、女声、不同音高、普通话口音差异；条件不足时记录覆盖限制。
5. 安静环境、键盘声、风扇声、远距离、轻度回声和不同信噪比。
6. 中英文、数字、百分比、人名、辩论术语和长句标点。
7. 句首第一个字和结束前最后一个字是否被 VAD 截掉。
8. 临时字幕是否重复、回退、闪烁或覆盖错误；最终字幕是否稳定去重。
9. 用户点击结束发言后最终结果等待时间，是否有“正在整理字幕”反馈。
10. 网络断开、WebSocket 重连、分片丢失、重复分片和乱序时的恢复。
11. TTS 扬声器声音是否被麦克风再次识别，形成回声字幕或污染对手历史；检查回声消除和播放期间录音策略。
12. 空白音频是否错误产生文字，长静音是否一直占用发言状态。
13. ASR 失败时是否保留音频、允许重试或人工修正，而不是直接丢失本次发言数据。

为 ASR 样本记录：

```md
| ID | 场景 | 参考文本 | 音频时长 | 首个临时结果 | 最终结果延迟 | CER | 首尾截断 | 重复/闪烁 | 标点 | 断线恢复 | 结论 |
|---|---|---|---:|---:|---:|---:|---|---|---|---|---|
```

建议质量门槛：

- 安静普通话标准语料 CER 中位数 ≤ 8%，P95 ≤ 15%。
- 首个临时字幕理想 ≤ 500ms；结束发言后最终字幕理想 ≤ 1.5 秒，P95 ≤ 3 秒。
- 固定语料不得稳定出现句首/句尾截断、整句重复或跨房间字幕。
- 空白音频不得生成实质性内容；TTS 播放不得污染人类 ASR。

### J-5、人机语音端到端体验

在真实 1v1 和 4v4 比赛中检查：

1. 人类发言结束 → 最终字幕 → 下一阶段提示 → AI 生成 → TTS 播放的连续性，避免长时间死寂。
2. AI 文字、网页字幕和最终音频内容是否一致；不能文字有一段、声音少一段。
3. 当前发言者头像、席位高亮、字幕和声音来源是否一致。
4. AI 播放时人类发言按钮必须正确禁用，并解释何时可发言。
5. 音频未播放、播放失败或用户静音时，比赛是否仍有可理解的视觉进度和字幕。
6. 观战页默认静音、主动解锁音频、音量记忆和移动端自动播放限制是否合理。
7. 进入下一阶段前是否有自然间隔和明确提示，而不是声音刚结束画面立即跳变。
8. 多音色之间响度、语速和质量是否一致，不因某个音色明显较差破坏公平感。

### J-6、语音问题修复要求

发现语音问题后不能只在前端隐藏现象，必须定位到具体层级：Agent 正文/思考分离、稳定短语提交、MOSS 参数、Prompt 音频、Codec、PCM 队列、LiveKit 发布、Opus/WebRTC、浏览器 AudioWorklet、状态机、FunASR 分片、VAD 或 WebSocket。

常见改进方向包括但不限于：

1. 按稳定短语和语义提交正文，禁止逐字提交，也不得等待完整长句；一轮始终复用同一 MOSS session。
2. 先定位源 PCM、LiveKit/Opus 或浏览器播放层，再决定是否处理边缘；不得对可靠链路盲目叠加低通、限幅、扩大缓冲或分段音频拼接。
3. 建立人名、辩论术语、英文缩写和多音字发音词典；不要用替换显示文本的方式污染逐字稿。
4. 只有在明确音色或源 PCM 缺陷且完成隔离 A/B 后，才调整 MOSS Prompt、语速或音色；不得绕过可靠音频发布门。
5. 为 MOSS 建立有界队列、房间隔离、取消令牌、正常完成/异常中断分离的超时、有限重试和 orphan 监控。
6. 实时公网传输固定验证 WebRTC Opus；PCM 只在服务器内部使用，历史回放可异步生成 Opus 衍生文件。
7. 为 ASR 增加麦克风预检、音量指示、尾部等待、去重、最终结果确认、断线重发和回声控制。
8. 所有修复必须保留原始文本、原始音频引用和版本信息，保证研究数据可追溯。
9. 修复后使用相同固定语料生成前后对照，报告 CER、MOS、延迟、RTF、文件大小和卡顿变化。

语音专项必须单独给出 `ASR 质量分 / TTS 内容完整性分 / TTS 自然度分 / TTS 实时性分 / 浏览器播放稳定性分`，每项 0–100，并给出证据。任何一项低于 80，最终结论不得为“可发布”。
