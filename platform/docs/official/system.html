  • / 与页面路由 → Next.js（本机 12341）。
  • /api/* 与房间主 WebSocket → 两个 FastAPI 实例（12340 / 12342）。

权威规则

  • 创建比赛时固定自动流程模板版本；之后修改模板不改变本场流程。
  • 开赛时锁定席位，空位由系统选择 AI 人设，普通用户不配置模型参数。
  • 真人发言必须同时满足：比赛运行、轮到本席位、没有其他活跃发言、控制租约有效。
  • 每次状态变化写入追加式 MatchEvent；重复请求通过幂等键和事务锁防止重复执行。
  • 外部服务连续失败时安全暂停，已有发言、计时和事件不得丢失。

提前生成策略

若下一阶段由 AI 发言，当前正式语音的完整 WAV 准备完成、单路 MOSS 端点释放后，Engine 会在该 WAV 稳定播放期间生成下一位辩手正文和完整语音。不得在当前正式 TTS 取得端点前排入投机 TTS；生产验证表明这会造成端点争用和取消恢复失败。正式进入下一阶段时只采用房间、阶段、席位、模板和历史指纹完全一致的预生成结果，否则取消并重新生成。

预加载不能改变比赛语义暂停、跳过、席位接管、文字校正或历史变化会使预生成内容失效。失效内容必须删除，不能“为了更快”继续播放。

容量边界

全站最多同时保留 5 个开放房间。所有房间合计最多 5 位匿名观众；参赛辩手、房主与系统管理员不占匿名观众名额。达到上限时必须给出明确拒绝，不进行无限重连。

完整源 WAV 保留用于回溯，播放文件以原子方式生成。全段完成后再连续发布，避免生成速度低于播放速度造成 underrun、杂音、撕裂或中途结束。变速使用整段保调时伸缩，不逐片段改变音色。

P0 判断“赛后录音正常、比赛现场卡顿”通常说明实时供给或播放缓冲不足，而不是模型音色坏。不得通过逐段 audio.play()、更小零缓冲或重复建连掩盖问题。

真人辩手

浏览器通过 AudioWorklet 采集 PCM，经鉴权的 /ws/rooms/:code/asr 桥接到 FunASR；识别结果写入字幕/文字稿。真人录音上传限制 50 MiB，Nginx 请求上限 52 MiB。浏览器不能直接假设标准 FunASR JSON 协议。

打断与回溯

暂停、跳过或终止必须同时取消 Agent/TTS 工作、停止 LiveKit 发布并清理未播放队列。归档保留实际发言、音频引用、事件和校验值；不能把用户未听到的生成内容当作完整已播发言。

认证与敏感信息

  • 密码使用 Argon2 哈希；登录会话使用 HttpOnly Cookie，写操作校验 CSRF。
  • Provider 密钥加密保存，API 和审计日志只返回“已配置”，不返回明文。
  • 浏览器按钮只负责提示，所有写操作仍在服务端校验用户、房间、席位、阶段和幂等键。
  • 匿名公开投影必须经过专用序列化，不得复用管理员/辩手完整 room snapshot。

数据生命周期

进行中状态写 PostgreSQL；Redis 只承载可恢复的短期协调状态。比赛完成、终止、待复核或结果修正后生成 JSON 归档与 SHA-256 校验。评分修正新增事件和补偿记录，不覆盖原始记录。

8. 部署与发布

生产根目录为 /home/ubuntu/sunsq/phdebate。Supervisor 管理 PostgreSQL、Redis、协作服务、双 API、Engine、Worker、Web、MOSS、Nginx 和备份任务。生产只对外暴露 HTTPS，不开放内部端口。

标准发布顺序

  1. 保存恢复点确认 Git 分支、数据库自定义格式备份、数据卷、私密配置和 GPU 语音运行时清单可验证。
  2. 运行质量门禁执行 ./scripts/quality.sh，至少覆盖本次改动对应的 API/Web/部署测试。
  3. 先升级 API 候选使用版本化虚拟环境或双 worker 滚动发布，影子端口通过 live/ready 后再切换。
  4. 再发布 Web通过 build-web-release.sh 创建不可变 release，健康后原子切换 .web-current。
  5. 重启 Engine/Worker仅在代码或配置需要时执行；检查进行中房间可恢复。
  6. 单场验收创建隔离比赛完成开始、AI/真人发言、语音、暂停恢复、结果和归档，再扩大验证。

9. 日常维护

每天检查

  • /api/health/ready 返回 200，数据库、Redis、磁盘、备份和外部服务状态可解释。
  • Supervisor 所有生产进程为 RUNNING，无持续重启或不断增长的错误日志。
  • 03:17 数据库备份成功且未超过 36 小时；最近恢复演练可完成。
  • 磁盘剩余空间高于安全线；音频、归档、release、源码归档按保留策略清理。
  • 没有长期占用上限的废弃大厅或暂停房间；不得直接在数据库随意删除有效比赛。

备份与恢复

10. 单场故障处置

先保护这场比赛，再排查平台。不得让学生反复新建房间来“绕过”故障。

  1. 确认唯一状态以房间 REST snapshot、最新 MatchEvent 和 Engine 日志判断是 preparing、running、paused、judging 还是 terminal；页面文案不能互相矛盾。
  2. 安全暂停若当前音频、Agent、ASR 或计时不可控，由房主/管理员在控制台暂停。保留阶段、剩余时间、当前 speech 和事件。
  3. 定位单一链路按“连接 → Agent 正文 → TTS 文件 → LiveKit 发布 → 浏览器可听”或“麦克风 → ASR WS → transcript”逐段核对，不同时修改多个变量。
  4. 原房间恢复优先 retry / resume；真人卡住时先结束当前发言或安全交给 AI，再恢复流程。只有数据已无法一致恢复时才终止。
  5. 完成后复盘导出房间事件、相关日志、音频校验和浏览器诊断，建立可重复测试；修复后用同一场景回归。

11. 测试与发布门禁

P0：先完成一场

  • 注册/登录 → 创建 1v1 或 4v4 房间 → 认领/准备 → AI 补位 → 开始。
  • 每个阶段按模板推进；只有正确辩手能发言；暂停、恢复和重连不丢状态。
  • AI 发言声音连续、无撕裂、音色一致、约 1.1×；真人 ASR 和录音可回溯。
  • 比赛进入 judging / completed 或明确 review_required，结果与事件一致。
  • 结果页可按权限查看录音、评分、积分和历史；匿名观众看不到文字稿。

随后扩大

再验证 4v4、多人抢座、多设备接管、最多 5 房间、全站 5 观众、跨房间隔离、Redis/数据库短暂故障、Engine 重启恢复、Agent/TTS/ASR 超时、移动端和无障碍。

证据要求

测试报告必须写明环境、代码 commit、数据是否临时、步骤、期望、实际、截图/事件/日志位置和清理结果。通过测试不等于没有风险；未覆盖范围要明确列出。
