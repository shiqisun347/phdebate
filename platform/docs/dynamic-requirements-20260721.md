# 动态需求评估与实施设计

日期：2026-07-21

本文把“自我辩论阶段”按上下文统一解释为“自由辩论阶段”。所有改动进入当前唯一平台版本，不建立第二套站点或 `/v2` 路径。

## 结论

七项需求都合理，但不能作为一个无边界的前端改版直接完成。它们涉及三条权威链路：

1. 比赛状态机：阶段切换、3 秒间隔、举手窗口、队列选择和 Agent 接替。
2. 文字数据：实时字幕、逐句片段、多人协同草稿、审核后权威文字和研究归档。
3. 语音热路径：主持播报、Agent 预生成、连续 TTS、取消和失效任务清理。

实施时继续冻结已经通过真实比赛验证的 MOSS/LiveKit/浏览器播放核心。新增能力通过状态机、房间事件、页面外层组件和独立协同服务接入，避免为一个 UI 需求破坏可靠语音基线。

## 逐项评估

### 1. 开场和换阶段主持播报

系统已经具备 `AudioCue`、管理员预设音频、准备阶段预生成、`audio.cue.ready` 事件和开场公告播放，开场能力不是从零开始。缺口是普通比赛阶段之间没有统一的主持播报协议。

实施方式：

- 每个内置目标阶段保留稳定 stage key，并绑定主持人口播 cue；不插入会破坏历史索引的额外阶段。
- 管理员上传的预设音频优先；含题目、姓名等动态变量时使用现有实时 TTS 后台预生成。
- 播报期间目标阶段在同一索引内临时投影为 `announcement`，服务端门控结束后恢复真实阶段类型。
- 播放结束或超时后才进入正式阶段；暂停、跳过、终止必须使旧 cue 失效。
- 不为每次换阶段重新建立 TTS/媒体连接，不修改已冻结的连续播放实现。

### 2. 多人协同文字记录面板

简单的“最后保存者覆盖前一个人”不满足多人同时编辑，也会污染研究数据。采用 Yjs CRDT，并以 Hocuspocus 作为独立 WebSocket 协同后端：

- 一个房间对应一个 Y.Doc；每条发言使用独立 `Y.Text`，避免编辑一条发言时锁住整场记录。
- Hocuspocus `onAuthenticate` 校验短期房间令牌，`onLoadDocument`/`onStoreDocument` 持久化二进制文档。
- awareness 只用于显示当前编辑者和光标，不作为权限或保存依据。
- 匿名观众只读；参赛者只能编辑自己的真人发言草稿；房主和管理员按审计权限处理。
- CRDT 内容是“协同草稿”，不是权威比赛记录。点击保存后仍进入现有发言修正申请和管理员复核链路，保留原文、建议文本、审核者、版本和时间。
- 同一个房间最多 20 名观众的限制不等于允许 20 人编辑；协同写权限按用户和发言逐条判断。

参考模式：Yjs 负责无冲突共享类型，`y-websocket` 提供 reconnect/awareness，Hocuspocus 提供认证、文档生命周期与数据库持久化。

### 3. 逐句字幕

现有舞台在 AI 完成后才获得完整 `Speech.content`，因此会长时间显示占位文字，最后短暂显示全文。新的字幕协议应与音频时间线绑定，而不是与最终全文绑定。

实施方式：

- 后端统一产生独立 `CaptionSegment` 展示投影：稳定 ID、speech ID、文字、顺序、是否 final 和展示偏移。
- AI 流式文本按稳定短句/逗号片段聚合后发布；ASR interim 继续实时展示，final 短句进入可恢复展示投影。
- 客户端按 segment ID 去重，“最新版本覆盖旧版本”，并按媒体时间显示当前片段。该模式参考 LiveKit transcription segment 的时间同步与 dedupe 设计。
- 文本切分参考 Pipecat `SentenceAggregator`：强标点立即成句，弱标点满足最小长度后输出，结束时 flush；不逐 token、逐汉字展示。
- 断线重连从房间快照恢复当前发言最近 40 个片段，不依赖只存在于浏览器内存的增量事件。
- AI 展示偏移标记为 `agent_text`，不冒充音频对齐；AI caption 不写入研究用 `TranscriptSegment`、裁判输入或研究导出。

### 4–6. 自由辩论举手、3 秒间隔和 Agent 决策

新增服务端权威 `FreeTurnRequest` 队列，不能只在浏览器维护举手顺序。

状态序列：

`一方开始发言 → 对方开放申请 → 当前发言结束 → 3 秒补充申请窗口 → 锁定队列 → 选择下一位 → 开始下一轮`

规则：

- 只有下一发言方的有效真人席位可以申请；再次点击取消。
- 窗口从对方 `speech.started` 开始，到对方发言结束后 3 秒截止。
- 排序使用服务端 `requested_at + id`，同一席位只有一个 pending 请求。
- 队首被选后，其余请求标记为本轮未选中；下一轮必须重新申请，防止永久霸占队列。
- 页面席位旁显示举手图标、顺序和申请时间；所有人看到同一权威队列。
- Agent 候选使用独立决策任务。对方发言结束并进入三秒窗口时，若当时无人申请，立即并发执行“是否应答”与“候选发言生成”，结果只进入带幂等任务 ID 的非权威暂存区。
- 若真人队列非空，真人优先，Agent 候选作废并触发取消。
- 若无人申请且 Agent 判断应答，使用已生成候选；判断为不应答时尝试下一 Agent。所有 Agent 均不应答时，使用受控兜底策略，避免自由辩论停死。
- 任何暂停、阶段切换、人工跳过或终止都必须取消决策、生成、TTS 和浏览器未播放队列。

举手的时间戳和显式清队列模式参考 Jitsi Meet；本系统仍由自己的比赛引擎决定谁获得发言权。

Round 20 已完成首个可靠版本：独立 `/debate/api/should-speak`、决定与隐藏候选并发、确定性幂等任务、fail-open、暂停/终止失效、中断和房间审计。推测在对方发言结束、三秒补充申请窗口开始时立即启动；真人申请会使其作废，窗口结束无人申请则复用同一结果，不重复调用。实现与验证见 `docs/qa/round20-free-agent-intent-20260721.md`。

### 7. Agent/TTS 预生成

预生成只优化等待时间，不能提前改变权威比赛状态。

- 当前发言最终文字固定后，在其 TTS 播放期间预生成下一位 Agent 的候选文字。
- 候选任务键包含 room、match、stage、turn、seat 和输入历史 hash；任一字段变化即失效。
- 本轮只预生成确定的下一固定 AI 阶段文字，不提前生成 TTS，因此不会绕过最多 2 场活跃 AI 语音比赛的资源限制。
- 只有下一发言者被状态机正式选中后才允许发布音频；未选候选只可缓存文字，或在有足够资源时生成不可公开的音频资产。
- 正式消费写入不含正文和密钥的命中事件；暂停、跳过、换人、历史或 Provider 快照变化会使进程内候选失效。

## 开源参考与采用边界

- [Yjs](https://github.com/yjs/yjs)：CRDT 共享数据类型。
- [y-websocket](https://github.com/yjs/y-websocket)：WebSocket 同步、awareness、断线重连模式。
- [Hocuspocus](https://github.com/ueberdosis/hocuspocus)：Yjs 服务端认证、加载、保存和数据库扩展。
- [LiveKit Components](https://github.com/livekit/components-js)：transcription segment 的稳定 ID、媒体时间和 dedupe。
- [Pipecat](https://github.com/pipecat-ai/pipecat)：完整句/短句聚合后再向下游输出。
- [Jitsi Meet](https://github.com/jitsi/jitsi-meet)：举手时间戳、取消和队列清理。

只采用接口和状态设计，不复制不明来源的产品 UI。依赖引入前固定版本并复核许可证；Yjs/y-websocket/Hocuspocus 为协同编辑的优先组合。

## 实施顺序

1. 完成现有发言修正闭环和 0028 迁移，确保文字修改有审计落点。
2. 增加 CaptionSegment 房间投影和逐句字幕 UI，先修复最直接的观看体验问题。
3. 增加文字记录 drawer；随后接入 Hocuspocus/Yjs 协同草稿与权限令牌。
4. 增加 FreeTurnRequest、3 秒 intermission 和服务端队列，再接入前端举手按钮与席位顺序。
5. 增加 Agent 决策/候选生成和失效清理。
6. 增加每阶段主持播报和下一 Agent/TTS 预生成，最后做多房资源与取消压力测试。

## 验收指标

- 字幕首句与首段可听音频时间差不超过 500ms；逐句可读，不出现最终全文只闪现约 1 秒。
- 两个浏览器同时编辑同一草稿不丢字；断线恢复后合并一致；无权限用户无法写入。
- 举手顺序在所有客户端一致；截止边界由服务端时间决定；重复请求、取消和并发请求幂等。
- 发言间隔为 3 秒，允许小于 250ms 的调度误差，不因 Agent 判断而无限等待。
- 预生成错误命中率为 0；暂停/终止后旧候选和旧音频不会复活。
- 四场不同房间同时运行时，队列、字幕、协同文档、Agent 候选和主持播报均不串房。
